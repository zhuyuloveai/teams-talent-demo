## 1. Background and goals

### 1.1 Business background

Customers can currently request a limit increase only through offline customer service, with no self-service channel, approval workbench, or progress feedback; the duties of limit change and approval are also not fully separated, and the approval evidence is scattered across tickets and emails.
This iteration provides customer self-service application, automated pre-review, manual approval, real-time limit effectiveness, and end-to-end audit.

### 1.2 Business goals (quantifiable)

| Goal | Quantified indicator |
|------|---------|
| Online application | 100% of limit increase applications handled online (the offline intake channel is closed after R2 goes live) |
| Shorter approval time | Average time from application to limit effectiveness drops from 3 days to 4 hours |
| Risk control | 0 incidents of approval beyond authority or beyond limits (counted in quarterly audits) |
| Better experience | Submit p95 < 1200ms; approval list p95 < 800ms |

### 1.3 Glossary

| Term | Definition |
|------|------|
| Permanent limit | A credit limit that remains effective in the long term; this iteration supports only this type |
| Automated pre-review | Automatic validation at submission time against delinquency, card tenure, number of limit increases, and product maximum |
| Initial review | The step in which a person verifies the documents and eligibility and gives a recommendation |
| Final approval | The step in which the approver makes an approve or reject decision and sets the new limit |
| SoD | Separation of duties, requiring that applicant and approver, and initial reviewer and final approver, are not the same person |
| Deduplication key | Business unique key generated by the client (API field `idempotencyKey`); repeated submissions with the same key return the same result |

## 2. User roles and permissions

| Role | Responsibility | Permission |
|------|------|--------|
| Cardholder | Submit limit increase applications, supplement documents, check progress | `limit:apply:self`, `limit:read:self`, `document:upload:self` |

## 3. Scope definition

### 3.1 In-Scope / Out-of-Scope

**In-Scope**

- Permanent limit applications (initiated by the customer).
- Customer application, document supplement, and progress query.
- Automated pre-review: delinquency, card tenure, number of limit increases in the past 6 months, product maximum.
- Workflow approval (initial review→final approval), limit update, notification, audit.
- Limit increase entry point on the front-end account page, application page, progress page; back-office approval workbench.

**Out-of-Scope**

- Automatic limit increase (initiated by the system).
- Limit decrease, restoration after temporary limit expiry.
- Income proof OCR and external credit bureau integration.

### 3.2 Assumptions and dependencies

| ID | Assumption/Dependency | Description |
|------|----------|------|
| A-01 | account-service provides APIs to read and update the limit | This iteration reuses `PUT /accounts/{id}` |
| A-02 | limit-service maintains limit definitions and the product maximum limit | The pre-review rule upper bound is taken from this service |
| A-03 | workflow-service provides approval tasks and to-do lists | Initial review and final approval are two task nodes |
| A-04 | document-service stores income documents and returns `documentId` | This requirement stores only the reference |
| A-05 | Delinquency data is provided by the statement or collections service | A read-only API is called during pre-review |

### 4.2 Detailed functional requirements

#### REQ-2026-003-01 "Apply for limit increase" entry point on the account page (REQ-LIM-01)

**Function description**: The account view shows the current limit and the limit increase button; the button is enabled when the account is `ACTIVE` and there is no in-progress application, and when an in-progress application exists the application status and entry link are shown instead.

**Field-level requirement table**:

| Field | Type | Required | Format/Validation | Default | Source |
|------|------|------|----------|--------|------|
| accountId | string(20) | Yes | 20-digit numeric string belonging to the signed-in customer | None | Route path parameter |
| accountStatus | string(16) | Yes | Only `ACTIVE` shows the enabled button | `ACTIVE` | account-service |
| creditLimit | decimal(12,2) | Yes | > 0, HALF_UP 2 decimal places | Current account limit | account-service |
| productMaxLimit | decimal(12,2) | Yes | ≥ `creditLimit`, taken from product configuration | Product maximum limit | limit-service |
| pendingApplicationId | string(32) | No | Returned when an in-progress application exists | Empty | limit-service |

**Exception matrix**:

| Exception scenario | System behavior | Error code | User message |
|---------|---------|--------|---------|
| Account not `ACTIVE` (hold/closed) | Button hidden | `LIMIT_NOT_ELIGIBLE` | "The current account status does not support a limit increase" |
| An in-progress application already exists | Button greyed out, "View progress" link shown | `LIMIT_APPLICATION_EXISTS` | "You have a limit increase application in progress" |
| Current limit already at the product maximum | Button greyed out | `LIMIT_REACHED_PRODUCT_MAX` | "The current limit has reached the product maximum" |
| account-service timeout (> 500ms) | Limit card shows retry | `DOWNSTREAM_UNAVAILABLE` | "Failed to load limit information, please retry" |

#### REQ-2026-003-02 Limit increase application form and submission (REQ-LIM-02)

**Function description**: The customer enters the requested limit, purpose, and income range, uploads documents as needed, and submits; submission triggers the automated pre-review, sets the application status to `SUBMITTED`, and creates the approval tasks.

**Field-level requirement table**:

| Field | Type | Required | Format/Validation | Default | Source |
|------|------|------|----------|--------|------|
| accountId | string(20) | Yes | Belongs to the current customer | Current account | Session context |
| requestedLimit | decimal(12,2) | Yes | > current limit and ≤ product maximum limit, HALF_UP 2 decimal places | None | Front-end form |
| purpose | string(16) | Yes | Enum `TRAVEL`/`EDUCATION`/`MEDICAL`/`DAILY`/`BUSINESS` | `DAILY` | Front-end dropdown |
| incomeRange | string(16) | Yes | Enum `0-10K`/`10K-20K`/`20K-30K`/`30K-50K`/`50K+` | Empty | Front-end dropdown |
| documents | array | No | Required when the requested limit > 2x the current limit, at least 1 `documentId` | Empty | document-service |
| idempotencyKey | string(64) | Yes | Client-generated, unique; repeated submission within 30 minutes returns the same application | None | Front end |
| status | string(16) | Yes | Initially `SUBMITTED` | `SUBMITTED` | limit-service |

**Exception matrix**:

| Exception scenario | System behavior | Error code | User message |
|---------|---------|--------|---------|
| Requested limit ≤ current limit | Form validation fails, submission rejected | `INVALID_REQUESTED_LIMIT` | "The requested limit must be higher than the current limit" |
| Requested limit > product maximum limit | Submission rejected | `LIMIT_EXCEEDS_PRODUCT_MAX` | "The requested limit must not exceed the product maximum of X" |
| An in-progress application already exists | Submission rejected | `LIMIT_APPLICATION_EXISTS` | "You have a limit increase application in progress" |
| Requested limit > 2x current limit and no documents uploaded | Submission rejected | `DOCUMENT_REQUIRED` | "Please upload income proof documents" |
| Document file exceeds 5MB or has a wrong type | Rejected during upload | `INVALID_DOCUMENT` | "Only PDF/JPG/PNG are supported, and a single file must not exceed 5MB" |
| Repeated submission with the same deduplication key | Returns the application created the first time | None (deduplication hit) | "Application submitted, redirecting to the progress page" |
| Pre-review service timeout | Application saved as `SUBMITTED`, pre-review retried asynchronously | `PRE_REVIEW_PENDING` | "Application received, the pre-review result will be shown shortly" |

#### REQ-2026-003-03 Automated pre-review (REQ-LIM-03)

**Function description**: Immediately after submission, four rule checks are executed (delinquency in the past 6 months, card tenure, number of limit increases, product maximum); if all pass, the status is set to `PRE_REVIEWED` and the application enters initial review; otherwise the status is set to `REJECTED` and the specific reason is shown.

**Field-level requirement table**:

| Field | Type | Required | Format/Validation | Default | Source |
|------|------|------|----------|--------|------|
| overdueMonths6 | int | Yes | Number of delinquent months in the past 6 months, must be 0 to pass | 0 | Statement/collections read-only API |
| cardAgeMonths | int | Yes | Months since card opening, must be ≥ 3 | Computed value | card-service |
| increaseCount6m | int | Yes | Successful limit increases in the past 6 months, must be 0 | 0 | limit-service |
| productMaxLimit | decimal(12,2) | Yes | `requestedLimit` ≤ this value | Product configuration | limit-service |
| preReviewResult | string(16) | Yes | Enum `PASSED`/`FAILED` | `PENDING` | limit-service |
| preReviewNote | string(128) | No | Required on failure, records the ID of the first rule hit | Empty | limit-service |

**Exception matrix**:

| Exception scenario | System behavior | Error code | User message |
|---------|---------|--------|---------|
| Delinquency in the past 6 months | Set to `REJECTED`, records BR-LIM-02 | `LIMIT_NOT_ELIGIBLE` | "There is a delinquency record in the past 6 months, so no limit increase is possible this time" |
| Card open for less than 3 months | Set to `REJECTED`, records BR-LIM-03 | `LIMIT_NOT_ELIGIBLE` | "You can apply for a limit increase once the card has been open for 3 months" |
| 1 successful limit increase in the past 6 months | Set to `REJECTED`, records BR-LIM-04 | `LIMIT_NOT_ELIGIBLE` | "A limit increase was already granted in the past 6 months, please apply again after 6 months" |
| Requested limit exceeds the product maximum | Set to `REJECTED` | `LIMIT_EXCEEDS_PRODUCT_MAX` | "The requested limit exceeds the product maximum" |
| Delinquency or card tenure data source unavailable | Pre-review set to `PENDING` and retried 3 times, then routed to manual handling | `PRE_REVIEW_PENDING` | "Pre-review in progress, the result is expected within 10 minutes" |

#### REQ-2026-003-04 Approval workbench and SoD (REQ-LIM-05)

**Function description**: The initial reviewer and the approver work on their to-do items in the workbench: viewing customer information, current and requested limits, card usage and delinquency, limit increase history, and documents; the initial reviewer gives a recommendation and the final approver approves or rejects. The system enforces applicant≠approver and initial reviewer≠final approver.

**Field-level requirement table**:

| Field | Type | Required | Format/Validation | Default | Source |
|------|------|------|----------|--------|------|
| applicationId | string(32) | Yes | Exists and has status `PRE_REVIEWED` or `REVIEWED` | None | Route path parameter |
| approvedLimit | decimal(12,2) | Yes | > current limit and ≤ `requestedLimit` | `requestedLimit` | Entered by the approver |
| decisionNote | string(256) | Yes | Required on rejection, length 10–256 | Empty | Entered by the approver |
| reviewer / approver | string(64) | Yes | Taken from the token, must not equal `applicant` | None | IAM token |
| dualApprovalRequired | boolean | Yes | true when `requestedLimit` > 2x the current limit | false | limit-service rule |
| secondApprover | string(64) | No | Required when `dualApprovalRequired` is true and must differ from `approver` | Empty | IAM token |

**Exception matrix**:

| Exception scenario | System behavior | Error code | User message |
|---------|---------|--------|---------|
| Approver = applicant | Operation rejected | `SOD_VIOLATION` (403) | "You must not approve an application you submitted yourself" |
| Final approver = initial reviewer | Operation rejected | `SOD_VIOLATION` (403) | "The final approver must not be the same as the initial reviewer" |
| Application status not pending (approved/rejected) | Operation rejected | `APPLICATION_NOT_PENDING` | "This application has already been processed" |
| No reason provided on rejection | Validation fails | `DECISION_NOTE_REQUIRED` | "A reason is mandatory for a rejection" |
| Dual approval required but the second approver is empty | Operation rejected | `DUAL_APPROVAL_REQUIRED` | "This limit requires dual approval" |
| Repeated submission of the same approval action | Returns the current status | None (deduplication hit) | "This application has already been processed" |

#### REQ-2026-003-05 Real-time limit effectiveness (REQ-LIM-06)

**Function description**: After final approval, account-service is called to update `creditLimit` and the limit definition in limit-service is synchronized; the status is set to `APPROVED` and a notification is sent. If the limit update fails, the application stays in `APPROVED_PENDING` and can be retried without repeating the approval.

**Field-level requirement table**:

| Field | Type | Required | Format/Validation | Default | Source |
|------|------|------|----------|--------|------|
| applicationId | string(32) | Yes | Status is `APPROVED_PENDING` or the approval moment | None | Request |
| newCreditLimit | decimal(12,2) | Yes | = `approvedLimit`, > 0 | `approvedLimit` | limit-service |
| effectiveAt | timestamptz | Yes | Moment of successful update, must not be earlier than `decidedAt` | Current time | account-service |
| status | string(16) | Yes | `APPROVED_PENDING` → `APPROVED` | `APPROVED_PENDING` | State machine |
| notificationStatus | string(16) | Yes | Enum `SENT`/`FAILED` | `SENT` | notification-service receipt |

**Exception matrix**:

| Exception scenario | System behavior | Error code | User message |
|---------|---------|--------|---------|
| account-service update fails | Status kept at `APPROVED_PENDING`, enters the retry queue (5-minute interval, at most 6 attempts) | `CREDIT_LIMIT_UPDATE_FAILED` | "Approved; the limit is being made effective" |
| limit-service limit definition synchronization fails | Rolls back this limit update, status stays `APPROVED_PENDING` | `CREDIT_LIMIT_UPDATE_FAILED` | "Approved; the limit is being made effective" |
| Limit update succeeds but the notification fails afterwards | Status set to `APPROVED`, failed notification queued for resending | None (main flow succeeded) | "The limit is now effective" |
| Still failing after 6 retries | Marks `APPROVED_PENDING` and routes to a manual ticket | `CREDIT_LIMIT_UPDATE_FAILED` | "The limit needs manual handling; customer service will contact you" |

> Note: REQ-LIM-04 (application progress timeline) and REQ-LIM-07 (audit and SoD), which are not expanded separately, are covered by the function list in 4.1, the business rules in Chapter 5, and the scenario matrix in Chapter 9; API definitions are in Chapter 7.

## 5. Business rules

| ID | Rule | Source | Priority | Verification point |
|------|------|------|--------|--------|
| BR-LIM-01 | The requested limit must be > the current limit and ≤ the product maximum limit | Simulated risk policy | Must | 8000→8000 rejected; 8000→25000 passes; 8000→25000.01 returns `LIMIT_EXCEEDS_PRODUCT_MAX` |
| BR-LIM-02 | No limit increase when there is delinquency or an unpaid minimum payment in the past 6 months | Simulated risk policy | Must | Fabricate 1 month of delinquency data; pre-review sets `REJECTED` and `preReviewNote` contains BR-LIM-02 |
| BR-LIM-03 | No limit increase when the card has been open for less than 3 months | Simulated risk policy | Must | Application with a card opened for 2 months is rejected, prompting that it can be applied for after 3 months |
| BR-LIM-04 | At most 1 successful limit increase per account within 6 months; only 1 in-progress application is allowed | Simulated risk policy | Must | The second application returns `LIMIT_NOT_ELIGIBLE`; concurrent submissions persist only 1 application |
| BR-LIM-05 | When the requested limit is > 2x the current limit, income documents must be supplied and dual approval is required | Simulated risk policy | Must | 8000→20000.01 without documents rejected; with documents `dualApprovalRequired=true` |
| BR-LIM-06 | The approver must not be the applicant or the initial reviewer (SoD) | Simulated compliance | Must | The same account acting in both roles returns 403 `SOD_VIOLATION` |
| BR-LIM-07 | After approval the limit takes effect immediately; a rejection must state a reason | Simulated risk policy | Must | Within 5 seconds after approval the account limit = `approvedLimit`; rejection without a reason returns `DECISION_NOTE_REQUIRED` |
| BR-LIM-08 | When the limit update fails, the application stays `APPROVED_PENDING` and can be retried | Simulated risk policy | Must | Approve after disabling account-service; the status is `APPROVED_PENDING` and it becomes effective automatically after recovery |

## 6. Non-functional requirements

### 6.1 Performance, availability, and observability

| Dimension | Metric | Verification method |
|------|------|---------|
| Performance | Submit p95 < 1200ms; approval list p95 < 800ms; limit effectiveness ≤ 5 seconds | Load test with 50 concurrent users; time the account limit polling after approval |
| Availability | Limit update failures can be retried without duplicate approval | Approve after disabling account-service; it becomes effective automatically after recovery |
| Consistency | Approval status and account limit are eventually consistent, with a discrepancy window ≤ 10 minutes | Reconciliation script compares `limit_application` with the account limit |
| Deduplication | Submission and approval operations support deduplication; repeated requests return the current status | Submit 3 times with the same deduplication key and assert the number of applications is 1 |
| Audit | Submission, pre-review, initial review, final approval, limit change, and notification result are all recorded | Query the event sequence in audit-service |
| Observability | Key nodes output traceId and `applicationId`; pre-review failure counts raise alerts | Inspect metrics and alert rules |

### 6.2 Security requirements

| Dimension | Requirement | Verification method |
|------|------|---------|
| Authentication | All APIs require a JWT issued by IAM; no token returns 401 | Call the 8 APIs without a token |
| Authorization | Customers can only read and write their own applications; approval APIs require role `A` with `limit:approve` | Call the approval API with a customer token and assert 403 |
| Non-forgeable identity | Applicant, initial reviewer, and approver identities are injected from the token and gateway; passing them from the front end is forbidden | Send a request with a forged `applicant` field and assert it is ignored |
| SoD | Applicant≠approver, initial reviewer≠final approver; violations return 403 | Perform two operations with a single account in both roles and assert both are rejected |
| Data protection | Income range and documents are visible only to authorized roles; logs do not print document content or file paths | Search the logs for document information beyond `documentId` |
| Document security | Type allowlist PDF/JPG/PNG, single file ≤ 5MB; downloads require authentication and write an audit record | Uploading an exe and a 6MB file is rejected in both cases |
| Audit | All decisions and limit changes are recorded and retained for 3 years | Spot-check event completeness for 10 applications |

### 8.2 Data security

| Dimension | Requirement |
|------|------|
| Masking | Customer names in the approval workbench list are shown as "surname + \*"; card numbers show only the last 4 digits; the income range is shown as an enum without the underlying amount details |
| Encryption | Income documents are stored encrypted by document-service (AES-256); this service stores only `documentId`; HTTPS at the transport layer |
| Retention | Application and approval records are retained for 5 years; income documents are automatically archived and deleted after 2 years; audit events are retained for 3 years |
| Access | Customers can only read their own applications; approvers can read applications and documents within their scope; document downloads require authentication and write an audit record; exported files expire after 24 hours |
| Minimization | Only purpose, income range, requested limit, and document references are collected; full income transaction details are not collected |

## 9. Scenario matrix

| Type | Scenario | Role | Data/API | Expected |
|------|------|------|-----------|------|
| Main flow | Limit 8000, apply for 12000, initial review and final approval pass | Cardholder + initial reviewer + approver | POST `/limit-applications` → `/review` → `/approve` | Status goes from `SUBMITTED` to `APPROVED`, the account limit becomes 12000 within 5 seconds, and the notification is sent |
| Main flow | Initial review rejects with a reason | Initial reviewer | POST `/admin/limit-applications/{id}/review` | Status `REJECTED`, the reason is shown on the customer progress page |
| Boundary | Requested limit = current limit × 2 (8000→16000) | Cardholder | POST `/limit-applications` | Dual approval is not triggered, `dualApprovalRequired=false` |
| Boundary | Requested limit = current limit × 2 + 0.01 (8000→16000.01) | Cardholder | POST `/limit-applications` | Dual approval is triggered, `dualApprovalRequired=true` |
| Boundary | Requested limit = product maximum 25000 | Cardholder | POST `/limit-applications` | Pre-review passes and initial review is allowed |
| Exception | 1 delinquent month in the past 6 months | Cardholder | POST `/limit-applications` | Pre-review sets `REJECTED` and shows the delinquency record |
| Exception | Second submission within 7 days for the same account | Cardholder | POST `/limit-applications` | 409 `LIMIT_APPLICATION_EXISTS` |
| Exception | Initial reviewer and final approver are the same account | Approver | POST `/admin/limit-applications/{id}/approve` | 403 `SOD_VIOLATION` |
| Exception | account-service unavailable after approval | Approver | POST `/approve` after disabling account-service | Status `APPROVED_PENDING`, becomes effective automatically after recovery, no duplicate approval |
| Exception | Upload a 6MB PDF as income proof | Cardholder | POST `/limit-applications/{id}/documents` | 400 `INVALID_DOCUMENT` |
| Permission | Customer A queries customer B's application | Cardholder | GET `/limit-applications/{id}` | 404, no data leakage |
| Permission | Risk control compliance account attempts to approve | Risk control/compliance | POST `/admin/limit-applications/{id}/approve` | 403, missing `limit:approve` |

## 11. Dependencies and constraints

### 11.1 Dependencies

| Dependency | Purpose | Failure impact and handling |
|---------|------|---------------|
| account-service | Limit read and update | Effectiveness failure keeps `APPROVED_PENDING` and retries automatically 6 times |
| limit-service | Product maximum and limit definitions | Pre-review is blocked, the application stays `SUBMITTED` |
| workflow-service | Initial review and final approval tasks | Approval to-dos are invisible; task creation is retried |
| document-service | Income document storage and authenticated download | Document submission failure returns `INVALID_DOCUMENT` |
| customer-service | Basic customer information | Fields are missing in the approval details; a placeholder is shown and an alert is raised |
| notification-service | Limit increase result notification | The main flow does not roll back; the notification is recorded for resending |
| audit-service | Audit events | Write failures go to a local compensation log |
| IAM | Authentication, roles, and SoD principals | No token returns 401 |

### 11.2 Impact analysis

| Dimension | Impact |
|------|------|
| Front end | Account view, application page, progress page, approval workbench, approval details |
| Back end | limit-service applications and rules; workflow approval; account limit update; document documents; notification notifications; audit auditing |
| Data | `limit_application`, `limit_application_document`; account limit version and audit events |
| APIs | 8 new APIs; the account response gains an "in-progress limit increase application" field |
| Configuration | Product maximum limit, approval roles, dual approval threshold (2x the current limit), notification templates |
| Testing | Eligibility rules, SoD, duplicate applications, limit effectiveness after approval, downstream failure retries |
| Documentation | This requirement, API catalog, approval permission matrix, limit increase policy description |

### 11.3 Constraints

- Reuse the existing limit-service and workflow-service; no new approval service is created.
- The approval roles and permission matrix must be aligned with IAM/RBAC before go-live.
- Amounts uniformly use `BigDecimal` / `numeric(12,2)`.
- All write APIs support deduplication keys; approval decisions cannot be overwritten, only appended.
- The demo environment reuses IAM roles `U`/`A`, and the POC does not perform strict API-level authorization (ADR-007), but SoD validation must be retained.

## 12. Risks and assumptions

### 12.1 Risks and mitigations

| Risk/Assumption | Impact | Mitigation |
|-----------|------|------|
| The limit increase eligibility rules (card tenure, count, income threshold) have not been formally confirmed by risk control | Frequent rule changes, high rework cost | All rules are configurable and support canary release; marked `SIMULATION` before v1.1 |
| Limit update and limit definition synchronization span two services | Inconsistent limits | account-service is authoritative; roll back and retry on failure; reconcile daily |
| Whether an external credit bureau query is needed is undecided | Biased pre-review conclusions | No credit bureau integration in this iteration; reserve the pre-review extension point `externalScore` |
| Approval roles are not aligned with IAM/RBAC | SoD validation is distorted | Complete the permission matrix review and persist role relationships before go-live |
| Assumption that one application maps to one account | Customers with multiple accounts must apply several times | Applications are independent per account; the front end provides account switching |
| Assumption that limit effectiveness ≤ 5 seconds | Customer-perceived delay | Effectiveness taking longer than 30 seconds raises an alert and sends an SMS telling the customer it is being processed |

### 12.2 Assumptions

- This iteration supports only permanent limit applications; temporary limits and limit decreases are out of scope.
- Appeals after a rejection go through a customer service ticket; no online appeal process is added.

### 12.3 Open items

1. The specific thresholds of the limit increase eligibility rules (open: risk control to issue the formal rule table; currently simulated values).
2. Whether a credit bureau query or external data source is required (open: risk policy to confirm; no integration in this iteration).
3. The calculation basis for the dual approval threshold (open: currently 2x the current limit).
4. The approval roles and permission matrix (open: to be persisted after alignment with IAM/RBAC).
5. The retention period for income documents (open: currently designed to be archived and deleted after 2 years, subject to legal review).
