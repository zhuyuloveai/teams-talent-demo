## 1. Background and goals

### 1.1 Business background

When customers have a question about a transaction they can only call customer service, documents are passed by email, and progress is not visible; dispute amounts, provisional credits, and chargeback deadlines are easily missed.
This iteration provides online transaction selection, reason and evidence submission, and progress tracking for customers, unified case handling in the back-office workbench, and automatic reminders for critical deadlines.

### 1.2 Business goals (quantifiable)

| Goal | Quantified indicator |
|------|---------|
| Online disputes | 90% of disputes handled online (compared with the share of phone intake in the 3 months before go-live) |
| Shorter first response | First case intake response < 4 hours |
| Deadline risk control | 0 overdue cases (SLA breaches counted quarterly) |
| Better experience | Case opening p95 < 1200ms; case list p95 < 800ms |

### 1.3 Glossary

| Term | Definition |
|------|------|
| Dispute case | Business document generated after a customer raises a question about a transaction; the status starts from `OPEN` |
| Reason code | Dispute classification, valued `FRAUD`/`UNAUTHORIZED`/`DUPLICATE`/`SERVICE_NOT_RECEIVED`/`OTHER` |
| Provisional credit | After review approval, the disputed amount is credited to the customer account first and later reversed or retained according to the outcome |
| chargeback | The process of raising a chargeback request with the card scheme |
| SLA | Case handling deadline: 1 business day for intake, 30 days for chargeback |
| Deduplication key | Business unique key generated by the client (API field `idempotencyKey`); repeated submissions with the same key return the same result |

## 3. Scope definition

### 3.1 In-Scope / Out-of-Scope

**In-Scope**

- Raise a dispute from the transaction details (reason code, description, amount, evidence files).
- Case progress, document supplement, case withdrawal.
- Back-office case workbench: intake, review, provisional credit, chargeback, closing.
- Integration with transaction, document, account, notification, audit.
- Deadline reminders: 1 business day for intake, 30 days for chargeback.

**Out-of-Scope**

- Direct connection to card scheme arbitration networks and automatic message exchange.
- Fraud investigation (deep integration with fraud-service).
- Multi-currency dispute conversion.

### 3.2 Assumptions and dependencies

| ID | Assumption/Dependency | Description |
|------|----------|------|
| A-01 | dispute-service already has the `dispute_case` table and a basic state machine | This requirement extends the fields and states |
| A-02 | Transaction snapshots are provided read-only by transaction-service | Disputes rely on the transaction snapshot and do not modify the original transaction |
| A-03 | Evidence files are stored in document-service | This service stores only metadata |
| A-04 | Provisional credit goes through the account-service credit API | `creditId` is identical to `provisionalCreditId` |
| A-05 | Notifications use notification-service templates | Notification failures do not roll back case handling |

### 4.2 Detailed functional requirements

#### REQ-2026-004-01 "Dispute this transaction" entry point on the transaction details (REQ-DSP-01)

**Function description**: The transaction details page shows the dispute entry point for eligible transactions; when a dispute is already in progress it shows the case entry point and status; when the transaction is not eligible the entry point is greyed out with the reason explained.

**Field-level requirement table**:

| Field | Type | Required | Format/Validation | Default | Source |
|------|------|------|----------|--------|------|
| transactionId | string(20) | Yes | 20-digit numeric string belonging to the current customer's account | None | Route path parameter |
| transactionStatus | string(16) | Yes | Only `POSTED` can be disputed | `POSTED` | transaction-service |
| postedDate | date | Yes | ≤ 90 days from today | Transaction posting date | transaction-service |
| disputeEligible | boolean | Yes | true/false, computed on the server | false | dispute-service eligibility field |
| existingCaseId | string(32) | No | Returned when a case is in progress | Empty | dispute-service |

**Exception matrix**:

| Exception scenario | System behavior | Error code | User message |
|---------|---------|--------|---------|
| Transaction not posted or already reversed | Entry point hidden | `DISPUTE_NOT_ELIGIBLE` | "The current transaction status does not support a dispute" |
| Transaction posted more than 90 days ago | Entry point greyed out | `DISPUTE_NOT_ELIGIBLE` | "Please call customer service for transactions older than 90 days" |
| A dispute is already in progress | Shows an "In progress" badge and navigates to the case details | `DISPUTE_EXISTS` | "This transaction already has a dispute in progress" |
| Transaction does not belong to the current customer | Returns 404 without disclosing the existence of the transaction | None (`404`) | "Transaction not found" |
| transaction-service timeout (> 500ms) | Entry point shows retry | `DOWNSTREAM_UNAVAILABLE` | "Failed to load the dispute entry point, please retry" |

#### REQ-2026-004-02 Dispute application and evidence upload (REQ-DSP-02)

**Function description**: The customer selects the reason code, enters the amount and description, uploads evidence, and submits; the system creates an `OPEN` case, saves the evidence metadata, computes the SLA due time, and notifies the customer and the specialist.

**Field-level requirement table**:

| Field | Type | Required | Format/Validation | Default | Source |
|------|------|------|----------|--------|------|
| transactionId | string(20) | Yes | Exists, `POSTED`, within 90 days, no dispute in progress | None | Front-end selection |
| accountId | string(20) | Yes | Matches the transaction ownership | Transaction account | Session context |
| reasonCode | string(24) | Yes | Enum `FRAUD`/`UNAUTHORIZED`/`DUPLICATE`/`SERVICE_NOT_RECEIVED`/`OTHER` | None | Front-end dropdown |
| amount | decimal(12,2) | Yes | > 0 and ≤ transaction amount, HALF_UP 2 decimal places | Transaction amount | Front-end form |
| description | string(500) | Yes | 10–500 characters, trimmed of leading and trailing spaces | Empty | Front-end input |
| evidenceCount | int | No | ≥ 1 for `FRAUD`/`UNAUTHORIZED`; each ≤ 10MB, ≤ 5 per case | 0 | document-service receipt |
| idempotencyKey | string(64) | Yes | Unique; repeated submission returns the same case | None | Front end |
| slaDueAt | timestamptz | Yes | = submission time + 1 business day (shifted when it falls on a non-business day) | Computed value | dispute-service |

**Exception matrix**:

| Exception scenario | System behavior | Error code | User message |
|---------|---------|--------|---------|
| A dispute is already in progress for the same transaction | Case opening rejected, returns the existing case number | `DISPUTE_EXISTS` | "This transaction already has a dispute in progress, please check the progress" |
| No evidence uploaded for `FRAUD`/`UNAUTHORIZED` | Case opening rejected | `EVIDENCE_REQUIRED` | "At least 1 piece of evidence is required for fraud or unauthorized transactions" |
| Dispute amount > transaction amount or ≤ 0 | Validation fails | `INVALID_DISPUTE_AMOUNT` | "The dispute amount must be greater than 0 and must not exceed the transaction amount" |
| Evidence file exceeds 10MB or has a wrong type | Rejected during upload | `INVALID_EVIDENCE` | "Only PDF/JPG/PNG are supported, and a single file must not exceed 10MB" |
| More than 5 evidence files for one case | Upload rejected | `EVIDENCE_LIMIT_EXCEEDED` | "At most 5 pieces of evidence per case" |
| Repeated submission with the same deduplication key | Returns the case created the first time | None (deduplication hit) | "Dispute submitted, redirecting to the case details" |
| document-service unavailable | The case is not created; the customer is asked to retry later | `DOWNSTREAM_UNAVAILABLE` | "Evidence upload failed, please retry" |

#### REQ-2026-004-03 Provisional credit (REQ-DSP-05)

**Function description**: After review approval, the specialist initiates the provisional credit and account-service is called to credit the customer account with the dispute amount; each case is credited only once, the case status is set to `PROVISIONAL_CREDIT` after crediting, and the customer can see the credit status and amount.

**Field-level requirement table**:

| Field | Type | Required | Format/Validation | Default | Source |
|------|------|------|----------|--------|------|
| caseId | string(32) | Yes | Status `UNDER_REVIEW`, exists | None | Route path parameter |
| creditAmount | decimal(12,2) | Yes | > 0 and ≤ dispute amount | Dispute amount | Entered by the specialist |
| provisionalCreditId | string(32) | Yes | Unique, passed as the account `creditId` | Generated by the server | dispute-service |
| creditReason | string(32) | Yes | Fixed `DISPUTE_PROVISIONAL` | `DISPUTE_PROVISIONAL` | dispute-service |
| approverRequired | boolean | Yes | true when `creditAmount` > 1000.00 | false | Rule configuration |
| status | string(16) | Yes | `UNDER_REVIEW` → `PROVISIONAL_CREDIT` | None | State machine |

**Exception matrix**:

| Exception scenario | System behavior | Error code | User message |
|---------|---------|--------|---------|
| Credit amount > dispute amount | Crediting rejected | `PROVISIONAL_CREDIT_EXCEEDS_AMOUNT` | "The provisional credit amount must not exceed the dispute amount" |
| Case already credited, request repeated | Returns the result of the first credit without crediting again | None (deduplication hit) | "This case has already received the provisional credit" |
| Case status not `UNDER_REVIEW` | Crediting rejected | `INVALID_DISPUTE_STATE` | "The current case status does not support a provisional credit" |
| Amount > 1000.00 without supervisor approval | Crediting rejected | `APPROVAL_REQUIRED` | "A high-value provisional credit requires supervisor approval" |
| account-service crediting fails | The case stays `UNDER_REVIEW` and `provisional_credit_id` is not written | `DOWNSTREAM_UNAVAILABLE` | "Provisional credit failed, please retry" |
| Crediting succeeds but the case write-back fails | Deduplicated replay keyed on `provisionalCreditId` repairs the case, and an alert is raised | `STATE_SYNC_PENDING` | "The credit has been received" |

#### REQ-2026-004-04 chargeback and case closing (REQ-DSP-06)

**Function description**: The customer and the specialist view chargeback progress in the case details; the specialist initiates the chargeback and closes the case after receiving the card scheme result (`WON`/`LOST`); on closing, the provisional credit is retained or reversed according to the outcome and a notification is sent.

**Field-level requirement table**:

| Field | Type | Required | Format/Validation | Default | Source |
|------|------|------|----------|--------|------|
| caseId | string(32) | Yes | Status allows chargeback or closing | None | Route path parameter |
| chargebackRef | string(32) | No | Filled in after the chargeback is initiated, unique | Empty | dispute-service |
| chargebackAt | timestamptz | No | Initiation time, ≤ transaction posting date + 30 days | Empty | dispute-service |
| won | boolean | Yes | Required on closing, taken from the card scheme result | None | Entered by the specialist |
| reverseCredit | boolean | Yes | true when `won=false` and a provisional credit was granted | Computed value | Settlement rule |
| status | string(16) | Yes | `CHARGEBACK` → `WON`/`LOST` → `CLOSED` | None | State machine |

**Exception matrix**:

| Exception scenario | System behavior | Error code | User message |
|---------|---------|--------|---------|
| chargeback initiated more than 30 days after the transaction posting date | Initiation rejected and escalated to manual handling | `CHARGEBACK_WINDOW_EXPIRED` | "The chargeback deadline has passed; a supervisor will escalate this case" |
| Case status does not allow closing | Closing rejected | `INVALID_DISPUTE_STATE` | "The current case status does not support closing" |
| Reversing the provisional credit fails during closing | The case stays `CHARGEBACK` and enters the retry queue | `DOWNSTREAM_UNAVAILABLE` | "Case closing in progress, please check again later" |
| Case closed repeatedly | Returns the result of the first closing | None (deduplication hit) | "This case has already been closed" |
| Closing result conflicts with the provisional credit direction (won=true but a reversal is requested) | Operation rejected with a rule conflict notice | `SETTLEMENT_CONFLICT` | "Case closing rule conflict, please contact a supervisor" |

#### REQ-2026-004-05 Deadline reminders (REQ-DSP-07)

**Function description**: Every day at 02:00 the system scans the SLA of open cases, notifies the specialist and supervisor 24 hours before the due time, marks overdue cases as `sla=breached` in the workbench, and escalates them to the supervisor.

**Field-level requirement table**:

| Field | Type | Required | Format/Validation | Default | Source |
|------|------|------|----------|--------|------|
| caseId | string(32) | Yes | Open cases | None | dispute_case |
| slaDueAt | timestamptz | Yes | 1 business day for intake or 30 days for chargeback | Computed value | dispute-service |
| slaState | string(16) | Yes | Enum `ON_TRACK`/`DUE_SOON`/`BREACHED` | `ON_TRACK` | Scan job |
| notifyTargets | array | Yes | At least 1 specialist and 1 supervisor | Case owner | Case relationship table |
| lastActionAt | timestamptz | Yes | Refreshed on every state transition | Creation time | dispute-service |

**Exception matrix**:

| Exception scenario | System behavior | Error code | User message |
|---------|---------|--------|---------|
| Case has no owner | Assigned to the default specialist queue and an alert is raised | `OWNER_MISSING` | Back-office notice "The case is unassigned and has been placed in the default queue" |
| notification-service unavailable | Recorded for resending and retried on the next scan | None (delayed notification) | Back-office notice "The reminder failed to send and has been queued for retry" |
| Case is closed during the scan | The case is skipped and no duplicate reminder is sent | None | No notice |
| Scan job is interrupted | Resumes from the breakpoint and deduplicates by `lastActionAt` | None (job re-run) | No notice |

## 5. Business rules

| ID | Rule | Source | Priority | Verification point |
|------|------|------|--------|--------|
| BR-DSP-01 | Only posted transactions can be disputed; the transaction date must be ≤ 90 days from today | Simulated business confirmation | Must | A 91-day transaction returns `DISPUTE_NOT_ELIGIBLE`; a 90-day transaction can be disputed |
| BR-DSP-02 | Only one dispute in progress per transaction | Simulated business confirmation | Must | Open cases twice concurrently; only 1 in-progress record exists in `dispute_case` |
| BR-DSP-03 | Dispute amount > 0 and ≤ transaction amount | Simulated business confirmation | Must | Amount 0 and an amount above the transaction amount both return `INVALID_DISPUTE_AMOUNT` |
| BR-DSP-04 | Reason codes FRAUD/UNAUTHORIZED/DUPLICATE/SERVICE_NOT_RECEIVED/OTHER | Simulated business confirmation | Must | All 5 reason codes can be submitted; an illegal value returns 400 |
| BR-DSP-05 | FRAUD/UNAUTHORIZED requires at least 1 piece of evidence | Simulated compliance | Must | Submission without evidence returns `EVIDENCE_REQUIRED` |
| BR-DSP-06 | Provisional credit requires review approval and an amount ≤ dispute amount; only one credit per case | Simulated funds policy | Must | A repeated credit returns the first result and the account balance increases only once |
| BR-DSP-07 | Case states: OPEN→UNDER_REVIEW→PROVISIONAL_CREDIT→CHARGEBACK→WON/LOST→CLOSED | Simulated business confirmation | Must | An illegal transition returns `INVALID_DISPUTE_STATE` |
| BR-DSP-08 | Customers can withdraw only in OPEN/UNDER_REVIEW; a case already provisionally credited requires supervisor confirmation | Simulated business confirmation | Should | Withdrawal of a `PROVISIONAL_CREDIT` case requires a supervisor token, otherwise 403 |
| BR-DSP-09 | All state transitions, evidence, and amount changes are audited; evidence access is recorded | Simulated compliance | Must | Audit events cover 5 kinds of action; evidence downloads produce access records |

## 6. Non-functional requirements

### 6.1 Performance, availability, and observability

| Dimension | Metric | Verification method |
|------|------|---------|
| Performance | Case opening p95 < 1200ms; list p95 < 800ms; evidence upload of a 10MB file < 10 seconds | Load test with 50 concurrent users; time the upload of a large file |
| Availability | Dependency failures return explicit error codes and the case status is unchanged | Disable account-service, initiate a provisional credit, and assert the case is still `UNDER_REVIEW` |
| Consistency | Provisional credit, closing reversal, and account balance are eventually consistent, with a discrepancy window ≤ 10 minutes | Reconciliation script compares cases with account credit records |
| Deduplication | Case opening, provisional credit, and closing support deduplication; repeated requests return the current status | Repeat the submission with the same deduplication key and the same `provisionalCreditId` and assert the amount changes only once |
| Deadline | The SLA scan runs daily at 02:00 and reminds 24 hours before the due time | Create a case due in 23 hours and assert the reminder event |
| Audit | State transitions, evidence, and amount changes are all recorded | Spot-check the event sequence of 10 cases |

### 6.2 Security requirements

| Dimension | Requirement | Verification method |
|------|------|---------|
| Authentication | All APIs require a JWT issued by IAM; no token returns 401 | Call the 10 APIs without a token |
| Authorization | Customers can only access their own cases; evidence downloads require the identity of the case customer or the handling specialist | Use customer A's token to download customer B's evidence and assert 403 |
| Privilege escalation protection | A customer accessing a case that is not theirs returns 404 without disclosing the existence of the case | Send a cross-customer access request |
| Evidence security | Type allowlist PDF/JPG/PNG, single file ≤ 10MB, ≤ 5 per case; downloads are audited | Uploading an executable file and an oversized file are both rejected |
| Data protection | Card numbers in logs and responses show only the last 4 digits; the description field filters HTML and scripts | Submit a description containing a script and assert it is escaped |
| Audit | State transitions, evidence access, amount changes, and closing are audited and retained for 3 years | Query the event completeness in audit-service |

### 8.2 Data security

| Dimension | Requirement |
|------|------|
| Masking | Customer names are shown as "surname + \*"; card numbers show only the last 4 digits; evidence file names are truncated in lists and downloads require authentication |
| Encryption | Evidence files are stored encrypted by document-service (AES-256); this service stores only metadata; HTTPS at the transport layer |
| Retention | Cases and evidence are retained for 7 years (simulated policy); audit events are retained for 3 years; expired evidence is archived by document-service |
| Access | Customers can only access evidence of their own cases; specialists can access cases they handle; supervisors can access all; every download writes an audit event |
| Minimization | No customer identity document images are collected; the description field filters HTML and scripts and is capped at 500 characters |

## 9. Scenario matrix

| Type | Scenario | Role | Data/API | Expected |
|------|------|------|-----------|------|
| Main flow | Dispute a posted transaction within 90 days as FRAUD with 1 PDF uploaded | Cardholder | POST `/disputes` + `/evidence` | 201, case `OPEN`, `sla_due_at` = submission time + 1 business day, the timeline is visible to the customer |
| Main flow | The specialist approves the review and initiates a provisional credit of 299.00 | Dispute specialist | POST `/admin/disputes/{id}/review` + `/provisional-credit` | Case `PROVISIONAL_CREDIT`, account credited 299.00, the credit status is visible to the customer |

## 11. Dependencies and constraints

### 11.1 Dependencies

| Dependency | Purpose | Failure impact and handling |
|---------|------|---------------|
| transaction-service | Transaction snapshot and eligibility | The entry point shows retry and no case is created |
| document-service | Evidence storage and authenticated download | Case opening fails or evidence is missing; the customer is asked to retry |
| account-service | Provisional credit and closing reversal | The case status is unchanged and enters the retry queue |
| notification-service | Case opening, credit, closing, SLA reminders | The main flow does not roll back; the notification is recorded for resending |
| audit-service | Audit events | Write failures go to a local compensation log |
| fraud-service | Fraud leads (reserved only in this iteration) | Does not block the main flow |
| IAM | Authentication, roles, and supervisor approval principals | No token returns 401 |

### 11.3 Constraints

- Reuse the existing dispute-service and `dispute_case`; no new dispute service is created.
- Evidence files are managed by document-service and this service stores only metadata.
- Amounts uniformly use `BigDecimal` / `numeric(12,2)`.
- All write APIs support deduplication keys; provisional credit and closing must support deduplication (double validation through `creditId` and case status).
- The demo environment reuses IAM roles `U`/`A`, and the POC does not perform strict API-level authorization (ADR-007), but case ownership validation must be retained.

## 12. Risks and assumptions

### 12.1 Risks and mitigations

| Risk/Assumption | Impact | Mitigation |
|-----------|------|------|
| The 90-day dispute window and the SLA deadlines are simulated values that have not been confirmed against card scheme rules | Case chargeback failures or overdue cases | All deadlines are configurable; compare against card scheme rules and issue a cross-reference table before go-live |
| The accounting entries and reversal strategy for provisional credit have not been aligned with Finance | Incorrect suspense postings | Credit the customer's available credit by default and make the accounts configurable; reconcile daily |
| Retaining evidence for 7 years incurs storage cost | Storage growth | document-service uses hot/cold tiering and moves data older than 1 year to low-frequency storage |
| Supervisor approval depends on someone being present | Delays in high-value crediting | Notify two people when the amount > 1000.00 and escalate if not approved within 4 hours |
| Assumption of ≤ 5 pieces of evidence per case | Insufficient evidence for complex cases | The limit is configurable and a supervisor can temporarily raise it to 10 |
| Single-point failure of the SLA scan job | Missed reminders | Job re-run mechanism + reconciliation of scan results |

### 12.2 Assumptions

- The card scheme result is entered manually by the specialist; no direct message exchange in this iteration.
- After a customer withdraws a case, the same case cannot be reopened; a new case must be opened (subject to the 90-day window).

### 12.3 Open items

1. The 90-day dispute window and the SLA deadlines (open: to be confirmed against card scheme rules and bank policy; currently simulated values).
2. The accounting entries and reversal strategy for provisional credit (open: Finance to confirm the accounts and the reversal trigger conditions).
3. The evidence retention period and privacy compliance (open: Legal to confirm the 7-year retention and archiving method).
4. The scope of fraud case linkage with fraud-service (open: only reserved lead fields in this iteration).
5. The high-value provisional credit threshold of 1000.00 (open: supervisor approval scope).
