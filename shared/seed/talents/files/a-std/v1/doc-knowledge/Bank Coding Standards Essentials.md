## 1. Layering and dependencies

```
com.cardcore.<context>
├── interfaces/rest      Inbound adapters: controllers, request / response DTOs
├── application          Application services: use case orchestration, transaction boundaries
├── domain               Aggregate roots, entities, value objects, repository ports, domain exceptions
└── infrastructure       Persistence, clients that call other services, configuration
```

- Dependency direction: `interfaces → application → domain ← infrastructure`.
- domain depends neither on Spring Web nor on other services.

## 2. Modeling conventions

| Convention | Description |
|---|---|
| Rich domain model | Domain behavior lives on entities, such as `account.applyPosting(amount)`; do not pile setters into services |
| Identifiers | Account ID 11 digits, card number 16 digits, customer ID 9 digits, transaction ID 16 digits; always zero-padded strings, never `long` |
| Amounts | `BigDecimal`, database `numeric(12,2)`, never `double` |
| Dates and times | `LocalDate` (`YYYY-MM-DD`), `LocalDateTime` |
| Status codes | Keep the legacy values: `Y/N`, `A/U`, `00/05` |
| Concurrency | Every aggregate table has `version`; entities use `@Version` |

Source: Credit card core business documents / design/07-java-conventions.md §3, §6

## 3. API conventions

- Base path `/api/v1/<plural resource>`; DTOs are Java `record`s, and request DTOs carry Jakarta Validation annotations.
- Lists always return `{"items": [...]}`, with `page`, `size` and `total` when paginated.
- Error responses are always `{"code", "message", "details"}`.
- HTTP semantics: `400` parameter validation failed, `404` not found, `409` business rule conflict, `503` downstream unavailable.

Source: Credit card core business documents / design/07-java-conventions.md §4

## 4. Five categories of check rules

| Category | Check | Severity |
|---|---|---|
| Naming | Naming rules for classes / methods / variables / constants; no pinyin abbreviations | Warning |
| Exceptions | No swallowed exceptions or empty catch blocks; failed inter-service calls throw `RemoteServiceException` and must not be swallowed | Major |
| Logging | Key operations are logged; **never log sensitive fields such as card numbers, SSNs or passwords** | Major |
| Security | Parameterized queries, no hard-coded secrets, input validation | Critical |
| Resources | Connections / streams / locks are released correctly, using try-with-resources | Major |

- Critical items block the commit, major items must be fixed, and warnings need an explanation or a tracking ticket.
- Changes involving fund transfers, key handling, regulatory reporting or third-party payment integration are automatically escalated to L3 checks.

Source: Bank Development Standards / Coding standards checklist; Bank Development Standards / Rule-to-tool mapping

## 5. Testing and databases

- Every service has at least domain behavior unit tests (plain JUnit) and one `@SpringBootTest` + `MockMvc` end-to-end case.
- Assert business rules and error codes, not logs or implementation details; tests do not depend on external networks.
- Each service has its own database and cross-database JOINs are forbidden; Flyway scripts are `V1__<context>_schema.sql` and `V2__<context>_seed.sql`, and seed data is idempotent.
