## 1. Background and Goals

### 1.1 Business Background

Customers want to spread the amount owed over several months on the statement date or after a large purchase in order to reduce short-term repayment pressure; the current system only supports full repayment and has no installment product.
This phase pilots 3/6/12-period installments for platinum/gold customers, building up installment plans, repayment schedules, and early settlement capabilities as a foundation for later differentiated fee rates.

### 1.2 Business Goals (Quantifiable)

| Goal | Quantified metric |
|------|---------|
| Increase installment penetration | Installment penetration among platinum/gold customers rises from 8% to 15% (measured 90 days after launch) |
| Increase fee income | Installment fee income grows 12% month over month (against the 3-month average before launch) |
| Shorten the application path | Time from application to plan creation < 3 seconds (p95, local Compose baseline) |

### 1.3 Glossary

| Term | Definition |
|------|------|
| Single-purchase installment | An installment product that takes one posted purchase as the object and spreads the principal evenly over 3/6/12 periods |
| Statement installment | An installment product that takes the amount due on the current statement as the object and spreads the principal evenly over 3/6/12 periods |
| Fee rate | Monthly fee rate, charged period by period on the remaining principal: 0.60% for 3 periods, 0.55% for 6 periods, and 0.50% for 12 periods |
| Rounding residual | The rounding difference after dividing the principal by the number of periods, absorbed by the last period |
| Deduplication key | A business-unique key generated by the client (API field `idempotencyKey`); resubmitting the same key returns the same result |
| Early settlement | The action of repaying the remaining principal in one lump sum and closing the installment plan |

## 3. Scope Definition

### 3.1 In-Scope / Out-of-Scope

**In-Scope**

- Single-purchase installment (3/6/12 periods) and statement installment (3/6/12 periods).
- Calculation and preview of period count, fee rate, fees, per-period principal, and per-period fees.
- Installment plans, repayment schedules, early settlement.
- Front-end entry points, plan page, back-office query.
- Integration with transaction, account, billing, ledger, notification, and audit.

**Out-of-Scope**

- Merchant subsidies, zero-fee campaigns, combined installments.
- Overdue penalty interest and credit bureau reporting (the existing statement and collections flows are reused).
- Multi-currency installments.

### 3.2 Assumptions and Dependencies

| ID | Assumption/Dependency | Description |
|------|----------|------|
| A-01 | The transaction has been posted by transaction-service and marked `POSTED` | Installment eligibility requires this status |
| A-02 | The installment-eligible statement amount is calculated and provided by billing-service | Statement calculation logic is not changed in this phase |
| A-03 | Limit reservation and release are completed through account-service | Changes affecting balances are never written directly by this service |
| A-04 | Fee income is posted to ledger-service | The existing fee accounts are reused |
| A-05 | Notifications use notification-service templates | Notification failures do not roll back the installment main flow |

### 4.2 Detailed Functional Requirements

#### REQ-2026-001-01 "Apply for installment" entry on transaction details (REQ-INS-01)

**Description**: On the transaction details page, show an "Apply for installment" button for eligible single purchases; when a purchase is not eligible, grey out the button and show the specific reason so that customers do not enter the flow only to fail.

**Field-level requirement table**:

| Field | Type | Required | Format/Validation | Default | Source |
|------|------|------|----------|--------|------|
| transactionId | string(20) | Yes | 20-digit numeric string; must belong to the current logged-in customer | None | Route path parameter |
| transactionAmount | decimal(12,2) | Yes | The entry is available only when ≥ 100.00 | Transaction amount | transaction-service |
| transactionStatus | string(16) | Yes | Only `POSTED` counts as installment-eligible | `POSTED` | transaction-service |
| installmentEligible | boolean | Yes | true/false, computed on the server; the front end must not infer it | false | transaction-service installment eligibility field |
| ineligibleReason | string(64) | No | Enum: `AMOUNT_TOO_LOW`/`ALREADY_INSTALLED`/`DISPUTED`/`DELINQUENT` | Empty | transaction-service |

**Exception matrix**:

| Exception scenario | System behavior | Error code | User message |
|---------|---------|--------|---------|
| Transaction amount < 100.00 | Grey out the button; clicking does nothing | `INSTALLMENT_NOT_ELIGIBLE` | "A single purchase of 100.00 or more is required to apply for an installment" |
| Transaction already on an installment plan | Show an "Already installed" badge; clicking opens the plan details | `ALREADY_INSTALLED` | "This transaction is already on an installment plan; view the installment plan" |
| Transaction in dispute or already overdue | Hide the entry | `INSTALLMENT_NOT_ELIGIBLE` | "The current status of this transaction does not support installments" |
| Transaction does not belong to the current logged-in customer | Return 404 without revealing that the transaction exists | `INSTALLMENT_NOT_FOUND` | "Transaction not found" |
| transaction-service timeout (> 500ms) | Show a retry button in the entry area | `DOWNSTREAM_UNAVAILABLE` | "Failed to load the installment entry; click to retry" |

#### REQ-2026-001-02 Installment preview (REQ-INS-03)

**Description**: After the customer selects 3/6/12 periods, show the per-period principal, per-period fee, first-period total, and total fees in real time; the preview is not persisted and returns a preview token for reuse on submission.

**Field-level requirement table**:

| Field | Type | Required | Format/Validation | Default | Source |
|------|------|------|----------|--------|------|
| accountId | string(20) | Yes | 20-digit numeric string with ownership validation passed | Current account | Session context |
| sourceType | string(16) | Yes | Enum `TRANSACTION`/`BILL` | None | Front-end selection |
| sourceId | string(32) | Yes | 20-digit transaction ID or 32-digit statement ID | None | Front-end selection |
| principal | decimal(12,2) | Yes | > 0 and ≤ installment-eligible balance; ≥ 100.00 for a single purchase, ≥ 500.00 for a statement | Installment-eligible balance | Front-end form |
| termMonths | int | Yes | Only 3/6/12 allowed | 6 | Front-end selection |
| monthlyFeeRate | decimal(6,4) | Yes | 0.0060 for 3 periods, 0.0055 for 6 periods, 0.0050 for 12 periods | Mapped by period count | installment-service pricing table |
| firstPeriodTotal | decimal(12,2) | Yes | = per-period principal + per-period fee, HALF_UP to 2 decimals | Computed value | installment-service |

**Exception matrix**:

| Exception scenario | System behavior | Error code | User message |
|---------|---------|--------|---------|
| Period count not in 3/6/12 | Reject the preview | `INVALID_TERM` | "Only 3, 6, and 12 periods are supported" |
| Principal below the minimum installment amount | Reject the preview | `INSTALLMENT_NOT_ELIGIBLE` | "Installments start at 100.00 for a single purchase and 500.00 for a statement" |
| Principal exceeds the installment-eligible balance | Reject the preview and show the maximum installment amount | `PRINCIPAL_EXCEEDS_LIMIT` | "The maximum installment amount is X" |
| Preview token older than 30 minutes | Reject on submission and require a new preview | `PREVIEW_EXPIRED` | "The preview result has expired; please preview again" |
| billing-service timeout (> 800ms) | Return a retryable error without caching the result | `DOWNSTREAM_UNAVAILABLE` | "Preview failed; please retry later" |

#### REQ-2026-001-03 Submit installment (REQ-INS-04)

**Description**: On the confirmation page, after the agreement is checked and the deduplication key is generated, create the installment plan and repayment schedule, write an audit event, and send a notification; a failure in any downstream call never leaves a "fee charged but no plan" state.

**Field-level requirement table**:

| Field | Type | Required | Format/Validation | Default | Source |
|------|------|------|----------|--------|------|
| idempotencyKey | string(64) | Yes | Generated by the client, globally unique; resubmission within 30 minutes returns the original plan | None | Front end |
| accountId | string(20) | Yes | Consistent with the logged-in customer's ownership | Current account | Session context |
| principal | decimal(12,2) | Yes | > 0; must match the preview token amount | Preview value | Front-end form |
| termMonths | int | Yes | Only 3/6/12 allowed | Preview value | Front-end selection |
| previewToken | string(64) | Yes | Not expired, and the amount and period count match the preview | None | Preview response |
| agreementAccepted | boolean | Yes | Must be true | false | Front-end checkbox |
| planStatus | string(16) | Yes | Initially `ACTIVE` | `ACTIVE` | installment-service |

**Exception matrix**:

| Exception scenario | System behavior | Error code | User message |
|---------|---------|--------|---------|
| Duplicate submission with the same deduplication key | Return the plan created the first time (HTTP 200) without charging twice | None (deduplication hit) | "The installment has been submitted; redirecting to the plan" |
| An effective plan already exists for the transaction/statement | Reject creation | `ALREADY_INSTALLED` | "This transaction is already on an installment plan; view the installment plan" |
| Agreement not checked | Reject submission | `AGREEMENT_REQUIRED` | "Please read and accept the installment agreement first" |
| previewToken expired or amount mismatch | Reject submission and return to the preview step | `PREVIEW_EXPIRED` | "The preview result has changed; please preview again" |
| ledger-service posting fails | Roll back the plan and repayment schedule, leaving no half-completed state | `DOWNSTREAM_UNAVAILABLE` | "Submission failed and no installment was created; please retry" |
| Plan write and account limit reservation are inconsistent | Roll back the transaction and write an alert audit event | `DOWNSTREAM_UNAVAILABLE` | "Submission failed; please retry later" |

#### REQ-2026-001-04 My installments (REQ-INS-05)

**Description**: Customers view the installment list and details for their own accounts, including the repayment schedule, remaining principal, and period progress; results are paged, and any unauthorized access returns 404.

**Field-level requirement table**:

| Field | Type | Required | Format/Validation | Default | Source |
|------|------|------|----------|--------|------|
| accountId | string(20) | Yes | Ownership validation passed | Current account | Session context |
| status | string(16) | No | Enum `ACTIVE`/`SETTLED`/`CANCELLED` | All statuses | Front-end filter |
| page | int | No | ≥ 1 | 1 | Front-end paging |
| size | int | No | 1–100 | 20 | Front-end paging |
| remainingPrincipal | decimal(12,2) | Yes | ≥ 0, HALF_UP to 2 decimals | Computed value | installment-service |
| paidPeriods / termMonths | int / int | Yes | paidPeriods ≤ termMonths | 0 / period count | installment-service |

**Exception matrix**:

| Exception scenario | System behavior | Error code | User message |
|---------|---------|--------|---------|
| Query installments of an account that is not the caller's | Return 404 | `INSTALLMENT_NOT_FOUND` | "No installment record found" |
| size > 100 or page < 1 | Parameter validation fails | `INVALID_PARAMETER` | "Invalid paging parameters" |
| status set to an unknown enum value | Parameter validation fails | `INVALID_PARAMETER` | "Invalid filter condition" |
| Repayment schedule missing under the plan | Return the plan and flag a `SCHEDULE_INCONSISTENT` alert | `SCHEDULE_INCONSISTENT` | "The repayment schedule is incomplete; please contact customer service" |

#### REQ-2026-001-05 Early settlement (REQ-INS-06)

**Description**: The customer initiates early settlement from the plan details; the system previews the remaining principal, fee rebate, and penalty fee, and after confirmation settles the plan, releases the limit, and generates an adjustment entry.

**Field-level requirement table**:

| Field | Type | Required | Format/Validation | Default | Source |
|------|------|------|----------|--------|------|
| planId | string(32) | Yes | Exists, `ACTIVE`, belongs to the current customer | None | Route path parameter |
| settlementPrincipal | decimal(12,2) | Yes | = remaining principal, ≥ 0 | Remaining principal | installment-service |
| feeRebate | decimal(12,2) | Yes | ≥ 0, calculated by the rebate policy (policy pending pricing confirmation) | 0.00 | Pricing policy |
| penaltyFee | decimal(12,2) | Yes | = remaining principal × 1%, HALF_UP to 2 decimals | Computed value | Pricing policy |
| settlementTotal | decimal(12,2) | Yes | = remaining principal + penalty fee − fee rebate | Computed value | installment-service |
| settlementIdempotencyKey | string(64) | Yes | Unique; resubmission returns the first result | None | Front end |

**Exception matrix**:

| Exception scenario | System behavior | Error code | User message |
|---------|---------|--------|---------|
| Plan already settled or cancelled | Reject the settlement | `SETTLEMENT_NOT_ALLOWED` | "This plan is already settled; no further action is needed" |
| Plan does not exist or is not the caller's | Return 404 | `INSTALLMENT_NOT_FOUND` | "No installment plan found" |
| Duplicate submission with the same deduplication key | Return the first settlement result | None (deduplication hit) | "Settlement has been accepted" |
| Current-period repayment races with settlement (version conflict) | Optimistic locking rejects and asks for a refresh | `CONCURRENT_MODIFICATION` | "The plan status has changed; refresh and retry" |
| ledger-service settlement entry fails | The plan stays `ACTIVE` and the limit is not released | `DOWNSTREAM_UNAVAILABLE` | "Settlement failed and nothing was charged; please retry" |

## 5. Business Rules

| ID | Rule | Source | Priority | Verification point |
|------|------|------|--------|--------|
| BR-INS-01 | Single-purchase installment amount ≥ 100.00; statement installment ≥ 500.00 | Simulated business confirmation | Must | 99.99 is rejected with `INSTALLMENT_NOT_ELIGIBLE`; 100.00 can be submitted |
| BR-INS-02 | Only 3/6/12 periods; monthly fee rate 0.60%/0.55%/0.50% | Simulated pricing | Must | Preview results for the three period options match the pricing table item by item; other period counts return `INVALID_TERM` |
| BR-INS-03 | Per-period principal = principal/periods, with the last period absorbing the rounding residual; fees are charged as remaining principal × monthly fee rate, HALF_UP to 2 decimals | Simulated pricing | Must | 1000.00 over 6 periods: 166.66 per period, 166.70 for the last period, total = 1000.00 |
| BR-INS-04 | The same transaction or the same statement can be successfully installed only once; the deduplication key is unique | Simulated business confirmation | Must | Duplicate submissions return the same plan number and the `installment_plan` count does not change |
| BR-INS-05 | The limit occupied by an installment = remaining principal; early settlement releases it | Simulated business confirmation | Must | After plan creation the account installment occupation = 1000.00; after settlement it returns to zero |
| BR-INS-06 | Overdue, disputed, or already installed transactions cannot be installed | Simulated risk policy | Must | The entry is greyed out for these three transaction types, and calling the API directly returns `INSTALLMENT_NOT_ELIGIBLE` |
| BR-INS-07 | Early settlement charges a penalty fee of 1% of the remaining principal; fees already collected are not refunded | Simulated pricing | Should | With a remaining principal of 600.00 the penalty fee is 6.00 and `settlementTotal` = 606.00 minus the fee rebate |
| BR-INS-08 | A plan takes effect at T+1 after creation, and the first period falls into the next statement | Simulated business confirmation | Must | When the creation date is D, the first due date falls in a statement cycle after D+1 |

## 6. Non-Functional Requirements

### 6.1 Performance, Availability, and Observability

| Dimension | Metric | Verification method |
|------|------|---------|
| Performance | Preview p95 < 300ms; creation p95 < 1200ms (local Compose) | Run a load script with 50 concurrent users and take p95 |
| Consistency | All amounts HALF_UP to 2 decimals with no floating point; plan and repayment schedule amounts add up consistently | Unit tests cover the rounding residual; a reconciliation script compares totals |
| Deduplication | Creation and settlement must support deduplication; duplicate requests return the first result | Submit the same deduplication key repeatedly and assert that the plan count and the number of accounting entries do not change |
| Availability | When a dependency is unavailable, return a clear error code and never leave a half-completed funds state | Submit after stopping ledger-service and assert that no plan is persisted |
| Audit | Record the requester, period count, principal, fee rate, plan number, and operation time | Query audit-service events and check that all fields are present |
| Observability | Each API outputs a traceId and the business plan number | Inspect logs and Micrometer metrics |

### 6.2 Security Requirements

| Dimension | Requirement | Verification method |
|------|------|---------|
| Authentication | All APIs require a JWT issued by IAM; requests without a token return 401 | Call the 6 APIs without a token |
| Authorization | Account ownership is validated and any unauthorized access returns 404; back-office APIs are accessible only to role `A` | Use customer A's token to access customer B's plan |
| Input validation | Amounts, period counts, and enums are all validated on the server; the front end must not infer eligibility | Send requests with invalid period counts and negative amounts |
| Data protection | Logs and events keep only the last 4 digits of the card number; responses never return the full card number | Capture traffic and search logs for card numbers |
| Replay protection | Deduplication key + 30-minute time window; expired keys are rejected | Replay a request from 31 minutes ago |
| Audit trail | Creation, settlement, and back-office queries write audit events including actor and payload | Query audit-service events |

### 8.2 Data Security

| Dimension | Requirement |
|------|------|
| Masking | API responses and logs keep only the last 4 digits of the card number; customer names are shown as "surname + \*"; sensitive fields are filtered before JSON is persisted |
| Encryption | HTTPS at the transport layer; TLS enabled for database connections; no new fields require encryption at rest (this phase has only amounts and plan numbers) |
| Retention | Installment plans and repayment schedules are retained for 5 years per the simulated policy; audit events for 3 years; deduplication keys for the same period as the plan |
| Access | Customers can read only their own account data (unauthorized access returns 404); operations and risk are read-only; write operations are limited to customer service assistance scenarios and are audited |
| Export | Back-office export requires `installment:read:any`, files are valid for 24 hours, and the export action is audited |

| Type | Scenario | Role | Data/API | Expectation |
|------|------|------|-----------|------|

| Exception | Submit the same deduplication key 3 times | Cardholder | POST `/installments`, fixed idempotencyKey | The same plan_id is returned 3 times, and only 1 set of accounting entries exists |

| Permission | Operations triggers an assisted settlement | Customer service/operations | POST `/installments/{id}/early-settlement` with a token containing `installment:settle:assist` | 200, audit records the operations account as actor |

## 10. Acceptance Criteria (Executable)

| Story | Given | When | Then | Data preparation |
|------|-------|------|------|---------|

## 11. Dependencies and Constraints

### 11.1 Dependencies

| Dependency | Purpose | Impact of failure and handling |
|---------|------|---------------|
| transaction-service | Transaction status and installment eligibility fields | The entry shows a retry action and the application flow is not entered |
| billing-service | Installment-eligible statement amount | Preview fails and can be retried |
| account-service | Limit reservation and release | Submission rolls back and no plan is created |
| ledger-service | Fee and penalty fee entries | Submission or settlement rolls back and raises an alert |
| notification-service | Plan creation and settlement notifications | The main flow is not rolled back; the failed notification is recorded for redelivery |
| audit-service | Audit events | Write failures go to a local retry queue |
| IAM | Authentication and roles | Without a token, the response is 401 |

### 11.2 Impact Analysis

| Dimension | Impact |
|------|------|
| Front end | Transaction details, statement page, new application page, list/details page, back-office query page |
| Back end | New installment-service; installment eligibility in transaction, installment-eligible amount in billing, limit occupation in account, fee income in ledger, notifications in notification, auditing in audit |

### 11.3 Constraints

- The technology stack keeps the existing Spring Boot 3 / PostgreSQL / vanilla SPA and introduces no new framework.
- A new service `installment-service :8110` and database `carddemo_installment` are recommended; merging it into billing-service must be decided after review.
- Amounts uniformly use `BigDecimal` / `numeric(12,2)`; IDs follow the existing zero-padding or UUID conventions.
- Changes affecting balances must go through account-service; changes with accounting impact must be posted to ledger-service.
- All write endpoints must support a deduplication key; key operations write audit events.

## 12. Risks and Assumptions

### 12.1 Risks and Mitigations

| Risk/Assumption | Impact | Mitigation |
|-----------|------|------|
| The fee rate and penalty fee are simulated values without pricing confirmation | Revenue projections deviate after launch | After pricing is confirmed, only the pricing table configuration is replaced without code changes; mark it with `PRICING_RATE_SIMULATION` before v1.1 |
| The installment limit occupation basis (remaining principal vs total principal) is not aligned with account/authorization | Limit occupation is too high or too low, affecting available credit display | Use remaining principal as the default basis and confirm it jointly with account/authorization before launch |
| The T+1 effective time of the first period is coupled with the statement cycle | The first period may fall into the current statement, creating a duplicate amount due | Validate the statement cycle at plan creation; on conflict, defer to the next cycle and record an audit event |
| The preview token has a 30-minute validity window | Customers who stay too long fail on submission | The front end prompts a preview refresh when 5 minutes remain |
| Occasional downstream ledger timeouts | Customers submit repeatedly | Deduplication key + transaction rollback + a failure message asking for a retry |
| Assumption: at most 20 installment plans per account | Customers over the limit can no longer install | Confirm the cap together with pricing, and return a clear error code when it is exceeded |

### 12.2 Assumptions

- The demo environment keeps the existing Spring Boot 3 / PostgreSQL stack and the IAM roles `U`/`A`.
- The POC does not enforce API-level authorization (ADR-007), but account ownership validation must be retained.

### 12.3 Items to Be Confirmed

1. Fee rate, penalty fee ratio, and first-period effective time (to be confirmed: business and pricing issue a formal pricing table).
2. Whether the installment limit occupation is "remaining principal" or "total principal" (to be confirmed: align with the account/authorization basis).
3. The fee rebate policy for early settlement (to be confirmed: whether to rebate proportionally to unexpired periods).
4. Whether statement installments and single-purchase installments may be combined (to be confirmed: product and risk control provide the combination rules).
5. The cap on installment plans per account (to be confirmed: currently designed as 20).
