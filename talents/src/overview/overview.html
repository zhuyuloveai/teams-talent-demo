The first four sections answer four questions: what problem we solve, what we deliver, how it is deployed, and why we can pull it off. From Section 5 on is the background: the state of RSI, the gaps to close, the scenarios, the framework, the validation done so far, and the roadmap.

1. The core problem: the end goal, and what to tackle first

In one sentence

On a user's own repository, a coding agent keeps making the same kind of mistake: the user corrects it, and it does it again next time; switch to a new base model, and things that used to work quietly get worse. Today people fix this by hand: read the complaints, guess the cause, edit the prompts, ship, and watch again. This project makes that happen automatically on the iCode server: it turns mistakes from the user's existing sessions into replayable tasks, finds the cause, proposes a change, verifies it with paired runs, and finally hands the user an inspectable "evolution proposal" to approve.

The end goal: let the agent improve itself through real use

On iCode this takes four scenarios. They share one pipeline and differ only in data sources and evaluation focus (details in Section 7):

ScenarioWhat the user runs into (example)What we provide

B Model adaptationAfter switching to a new base model, a class of tasks that used to be stable quietly regresses, and nobody can say wherePaired reruns of old and new models on a fixed regression set; a per-category regression list and targeted harness fixes

The first class to tackle: change propagation completeness ("change one place, miss a path")

In the short term we take one class of problems from Scenario A, run the full loop end to end, and show the results. The class is: a piece of shared state (or a contract) has several read/write paths, the agent's change reaches only some of them, and the paths drift out of sync. The error is not in the code the agent wrote but in the code it did not write: an error of omission. That makes it hard for the agent to catch in self-review, and hard for a verifier that only tests the changed spot. One user described the mechanism precisely at the start of a session:

"This creates an inconsistency where stale sessions are cleaned up in some code paths but not others."
(cli-task-19def0-stale-session, session ev0, verbatim)

This is an old software engineering problem called change propagation; in code structure it shows up as shotgun surgery. Park et al. measured Eclipse and Mozilla and found that 22%–33% of bugs need a supplementary fix after the first one, and that missed changes are harder to spot than wrong ones (An Empirical Study of Supplementary Bug Fixes, MSR 2012, DOI 10.1109/MSR.2012.6224298). With a coding agent the problem takes a new form: human developers rely on experience and code review to cover the full propagation surface, while an agent sees only what is in its context.

Why this class first: in tasks built from real sessions this kind of requirement is common, and models clearly fail on it more often. Because the error sits where the agent wrote nothing, both self-review and verification that only tests the changed spot struggle to catch it, which is exactly what evolution is for. Grouped by "where the other path comes from", the class splits into five kinds (failure rates count only runs that were clearly right or clearly wrong):

How the three paths split the work: when to check, how far, and how we know

The three evolution paths (defined in Section 12) each own one part of this problem: A owns "when to check", triggering a check when a change touches shared state; B owns "how far to check", using code location and code analysis to find every path on the propagation surface from the changed spot and confirm each one is updated; C owns "how we know", supplying the dependencies and conventions from the code graph, development patterns and documents that code analysis cannot see. Doing only one of them fails in a predictable way:

Feasibility: most of the propagation surface for this class is structure that exists explicitly in the code, and B's code location and analysis can find it. In Gemini rewind, the seven write-backs each build their own path, but all are the same kind of write-back call; in Stale-session, the seven entry points all read the same state file; in Empty-repo, the missed Gemini hook has calls and error messages identical, word for word, to the Claude hook. What cannot be found is exactly what C has to supply: in the Attribution case the call graph cannot see the dependency "what attribution reads must come from the same source as the checkpoint", which takes two hops along the data source; and published code graph work only has file, class and function nodes with call and inheritance edges, with no "state" nodes or read/write edges.

On the base commit of each of the six cases, we checked offline whether C's four kinds of knowledge could have predicted the missed path in advance:

Knowledge sourceYes / Partly / NoNotes
Code-graph-style queries5 / 1 / 0Most effective, closest to B's code location; the Attribution case needs two hops along the data source to find it
Historical co-change2 / 3 / 1Second. It must be function-level (file-level is useless when the miss is in the same file), filter out high-traffic hub files, and tell good patterns from bad
Trajectory experience0 / 4 / 2Reuse signal beyond the same task is still weak and needs accumulation across sessions; user corrections are a natural supervision signal for "which path was missed"
Repository docs0 / 2 / 4Weakest. The docs for these tasks barely state invariants; the Prompt-source docs still describe the very behavior this change removes

This is a feasibility check, not a closed-loop experiment: "the code graph can find it" means a query simulated with code search on the base commit, and co-change uses only history before the base commit.

A loop already completed: 408b8c, v1→v7 (a boundary task for this class)

408b8c is a task where the full "attribute → propose a change → paired rerun → decide" loop has been run: the user wanted GetWorktreePath to be cacheable like RepoRoot; all three times iCode built a separate cache, and the user corrected it: "paths.RepoRoot() already implements the same cwd-keyed caching". It belongs to the "existing implementation" kind in the table above and is a boundary task for this class: the agent read the existing implementation and still wrote another one, so what was missing was judgment, not information. Looking through only one path, v1–v2 would be misread as "not capable enough" (in fact the change was never loaded), and v5 would be misread as "this direction works" (in fact the trigger scope broke). Across 3 regression tasks and 5 valid runs, no checkpoint went from pass to fail because of v7. The evidence is one target task and a single model, far from enough to say this class of problem is solved.

Short-term roadmap

  1. Task set: the target tasks are Gemini rewind, Prompt-source, OpenCode-native, Session-agent and Attribution, all in this class and all failed by the model; Stale-session and Empty-repo serve as controls. First remove the hints from the task statements and make a version that gives only the original requirement without naming the paths; only then can we really measure the ability to "cover the propagation surface".
  2. Verifiers: for every task, deliberately break one of the paths and confirm the verifier catches it; verifiers can miss paths too.
  3. Knowledge (offline, can start now): build a state read/write graph and a function-level co-change table on entireio/cli, replay history on the six cases, and see whether the predicted propagation surface includes the missed paths.
  4. Closed loop: A adds triggers, B adds code location, change impact analysis and cross-path test generation, C adds the knowledge above; compare v0 against each combination on the hint-free task statements, with held-out tasks stratified by subclass.
  5. Generalization: add tasks from multi-variant product sessions outside entireio/cli (multiple platforms, protocol versions, tenant configurations) to test whether "multiple implementations" is just a quirk of this one repo.

3. How it is deployed: alongside the iCode server, invisible to users

The Talents platform is deployed alongside the iCode server (in the cloud or inside the customer domain). It triggers evolution automatically on the server side, using trajectories iCode already receives, and is invisible to users. Users take part in only two places: at onboarding, they provide a runtime environment where the main branch builds and all tests pass; once evolution has results, they review and confirm an "evolution proposal" in the portal.

Why deploy alongside the iCode server

Trajectories are already on the server

iCode sessions, tool calls and model requests all pass through the server and the model gateway. With Talents deployed next to them, users do not export or upload anything. That is what makes it invisible to users, and what keeps data inside the domain.

Evolution runs on the server

Building tasks, running evaluations and trying changes are batch container jobs. They run on the server-side evaluation cluster, within each tenant's budget and during idle hours, using none of the user's machines or time.

Changes take effect from the server

Skills, tools, prompts and knowledge entries the user confirms are pushed by the server to iCode clients as "repository-level / team-level configuration"; clients need no upgrade.

There are two deployment packages: cloud (with the iCode cloud service, isolated per tenant) and in-domain (with private iCode deployments, data stays in the domain). Evolution is triggered by new sessions piling up, a new base model going live, changes to the skill library, or a manual request, and everything queues in the background: the only thing users notice is a new "evolution proposal".

Deployment architecture

The seven Talents components map one to one onto the seven work domains in Section 8 (each component in the figure shows its work domain on the right). They sit in the same data center / domain as the iCode server and have only two outputs: user-side configuration confirmed by users goes back to the iCode server and is pushed per repository; agent-side candidates, with scorecards, go to the iCode-Core release pipeline.

How users onboard: provide an environment, the platform checks the "green baseline"

① Register the repository

Repository URL, main branch, read-only access.

② Provide a runtime environment

A Docker image (or a Dockerfile / devcontainer config), plus the build command and test command.

③ Platform checks the green baseline

On the latest commit of the main branch, the user's image builds and all tests pass, with the same result on 3 consecutive runs. Inconsistent tests are listed for the user to resolve (fix them, or explicitly mark them "flaky, excluded from scoring"). The output is an onboarding report: build time, test count, list of flaky tests.

④ Authorize how trajectories are used

Only for this repository / team; whether anonymized data may contribute to general agent-side improvements (off by default).

Once done, the repository's status becomes "Connected", and the platform starts building tasks from its past sessions automatically.

From onboarding to rollout

User-side changes (skills, knowledge entries, repository-level prompts) are pushed per repository by the iCode server, or land in the user's repository as a merge request, with one-click rollback. Agent-side changes ship with official iCode releases and are reviewed jointly by iCode-Talents and iCode-Core; a single user cannot approve them.

4. Core strengths: more than building tasks

Our strengths come from several bodies of work stacked together: first, raw material others cannot get; then, the methods and experience to use it well. Ranked below by "how hard it is for others to catch up":

  1. Our position: private product repositories, executable environments and real sessions, all in hand. RSI needs real user tasks turned into tasks that can be rerun and scored automatically, and that takes all three. We have all three:

    • Private product repositories: iCode sessions happen on the company's own product repositories. They have full commit history, so we can go back to the start of a session and rebuild the scene; tasks come from real products, not open-source repositories or synthetic tasks.
    • Executable environments: users provide a runtime environment at onboarding and the platform checks the "green baseline" (Section 3), so tasks can be rerun and scored automatically.
    • Real sessions: from real iCode users, with multi-turn interaction and user corrections. Task statements and acceptance requirements come straight from the users' own words, so scoring targets what users actually care about.

    Others usually hold only part of this: those with user trajectories cannot get the repositories and environments, and those with repositories have no real user trajectories.

  2. Three paths combined, starting from the coding problem itself. Published evolution practice in industry is almost always single-agent: change that agent's components from the outside in (the six levels in Section 5 are all agent components). We split a coding failure into three kinds, "didn't use it (agent components) / can't do it (software engineering capability) / didn't know (knowledge)", route them to three paths, and then verify combinations on the same batch of tasks (for how the work splits on the short-term problem class, see Figure 1 in Section 1).

    Gains do not simply add up: a patch stacked on an already-evolved harness can score −15.7 (HarnessBank, arXiv 2607.13683, 2026-07). So combining the paths needs routing and criteria of its own; it is a capability, not stacking. The three bodies of prior work below each map to one path.

  3. Path A · Prior work on self-evolution: a loop built from scratch. Every link of the loop has the team's own work behind it; chained together they form the full pipeline from environments and task building to attribution, optimization and training:

    • Task building and environments: Change2Task (arXiv 2607.28591, 2026-07, under submission to ICLR 2027) builds tasks by injecting historical changes in reverse into the current healthy version, with a 79.6% construction success rate (900/1,130), −58.4% environment time and −71.2% storage. It solves exactly the deployment problem of "green baseline on the main branch, session on an old commit" (Section 3).
    • Attribution: DoVer (arXiv 2512.06749, ICLR 2026), interventional fault localization.
    • Optimization: AutoSaddler (arXiv 2608.23041, 2026-08, preprint), automatic harness optimization, i.e. path A itself.
    • Training: Agent Lightning (arXiv 2608.17528), an agentic RL framework, corresponding to the larger model-side loop.

    RepoLaunch and SWE-bench-Live serve as reference work. 408b8c's v1→v7 (Section 1) is this pipeline run for real on one task.

  4. Path B · Prior work in software engineering. The code location, code analysis, test generation and scoring that path B needs are exactly what the team has built up in software engineering, covering requirements, test generation, scoring, trajectory diagnosis, code evolution and reuse, and code reliability. Representative work:

    • Code evolution: Evolution-aware Constraint Derivation for Software Remodularization (TOSEM 2024): change impact analysis and dependency constraints, directly usable for the short-term problem class.
    • Test generation: Beyond Coverage (using LLMs to improve test suite effectiveness, OOPSLA 2026): confirming each path is updated.
    • Requirements: A Unified Issue Resolution Benchmark for Requirement Clarification, Planning, and Code Generation for Coding Agents (arXiv 2608.09072).
    • Scoring: Can LLMs Replace Human Evaluators? (ISSTA 2025).
    • Trajectory diagnosis: What Resolve Rate Hides (structural trajectory diagnosis for coding agents, arXiv 2607.06184).

  5. Path C · Prior work in knowledge engineering. The team has done three main things in knowledge engineering, which are exactly the three knowledge sources the short-term problem class needs: code graphs (code entities and dependencies; add state read/write edges and the propagation surface can be derived directly), development pattern mining (mining co-change rules like "when you change this, you usually also change that" from commit history), and RAG over document / text knowledge graphs (structuring the contracts and conventions in documents for retrieval).

    On top of that we did six in-depth literature reviews on knowledge engineering and arrived at a few constraints: writes must be incremental appends merged by deterministic code, because rewriting the whole thing can collapse a knowledge base in a single step (ACE measured a drop from 18,282 tokens / 66.7 points to 122 tokens / 57.1 points; ACE: Agentic Context Engineering, arXiv 2510.04618, ICLR 2026); every piece of knowledge must carry its own scope and trigger conditions; knowledge is specific to the model and the failure pattern, and transfer across scenarios is the real bottleneck.

  6. The evolution mechanism itself improves: the dual loop. The first-order loop changes how the agent works every round; the second-order loop reviews the first-order loop every few rounds and improves "how it proposes changes and how it judges whether they help"; later, the second-order correction signals train a process judge model (Section 12). Academia already has work on improving the evolution loop itself, and the shared conclusion is that there must be a fixed anchor the agent cannot change. Our anchors are tests, same-start comparisons and manual spot checks, all from real repositories.

    Status: the first-order loop has run end to end on 408b8c; the second-order loop is currently done by manual review; the process judge model is future work.

  7. Trustworthy criteria. Every task built must pass the D1–D9 gates; scoring is done by a verify agent that cannot see the reference patch and writes tests on the spot from the checkpoints (Section 9); on product repositories, line-level adoption (which lines the agent wrote that the user finally kept) can also be used in reverse to check whether the task set is trustworthy.

  8. More than "does it run". Most RSI work looks only at functional correctness, but code needs long-term human maintenance after it is written. We extract non-functional dimensions such as maintainability and readability from what users say and include them in evaluation (Section 13).

  9. Where it is deployed. Alongside the iCode server, trajectories are naturally available and users notice nothing; every connected repository adds more tasks and criteria, which get more accurate with use (see Section 3).

5. Where it comes from: the state of RSI and the window of opportunity

RSI (Recursive Self-Improvement) means an AI system modifies its own code, configuration or strategy, with the changes persisted and affecting later versions, forming a compounding improvement loop. Self-correction within a single round, or optimization where a human decides every step, does not count.

Academia: the design space is mapped out, scale has not kept up

From single-layer optimization (2024: DSPy and OPRO tuning prompts) to whole-harness optimization (2026), people have worked on skill libraries, memory, topology and weights. But experiments stay at a few hundred tasks; generalization shrinks sharply (+14 in-distribution, only +5 out of distribution); there are no production-ready safety defenses and no cost accounting.

Industry: everyone is evolving, nobody merges fully automatically

We surveyed the public practice of 16 companies along six levels (table below). Three patterns hold up after cross-checking multiple sources: first turn online fixes and user feedback into evaluation tasks, then let the agent propose candidate changes; offline evaluation and online A/B tests must both pass; candidates can be generated and drafted automatically, but releases still keep a human gate.

Why coding agents, and why now

Code can be executed and tested, and right and wrong can be judged objectively, which makes it the best testbed for RSI. Models are just capable enough (too weak and optimization does nothing, too strong and there is no room to improve), agent frameworks have stabilized, and industry has huge volumes of real trajectories. What is missing is infrastructure: a method to go from trajectories to tasks, reliable criteria, and a multi-dimensional optimization framework. These are the three gaps in the next section.

11. Three tiers of evolution: user side, agent side, model side

The three tiers are where a change lands, answering "who does the change apply to"; the three paths (see Section 12) answer "what is changed". These are two independent dimensions, and each path's changes land in a tier according to their scope:

  • Path A (agent components) changes components that exist only because there is an agent: user prompts, system prompts, skills, tools, the harness, memory. The same kind of component can apply only to one repository or team (user side, such as repository instruction files or project-level skills) or go into the agent mainline and apply to all users (agent side, such as system prompts or built-in tools).
  • Path B (software engineering capabilities) changes capabilities such as requirements engineering, code location, test generation and change impact analysis. People used and studied them before agents existed, and they are independent of the agent stack; now agents implement them, or they help improve agents. General capabilities go to the agent side; those that hold only for one repository (such as one repository's test conventions) stay on the user side.
  • Path C (knowledge engineering) works the same way: each piece of knowledge goes to the user side or the agent side according to its own scope.
  • Model-side evolution is separate (agentic RL, fine-tuning for specific capabilities). The framework can accommodate it, but it is not planned for 2026–27; what the dual loop in Section 12 will train later is a process judge model, not the base model.
TierWho it applies toHow it evolves
User sideOnly one repository or team; stays inside the domainExtract success patterns from that user's trajectories, annotate their scope, load them only on a match
Agent sideAll users; goes into the agent mainline, versioned and reversibleDistill common problems from many users' trajectories, verify generalization on a held-out set, confirm no negative impact with paired reruns and regression runs
Model sideEvery agent that uses the modelTrain weights with reward signals from the same tasks and trajectories; the framework can accommodate it, but it is not planned for 2026–27

12. Three evolution paths and the dual loop

The three paths are divided by "what is changed". A changes the agent's own components: prompts, skills, tools, the harness, memory; without the agent these concepts do not exist. B changes software engineering capabilities: requirements engineering, code location, test generation and so on. They predate agents and are independent of the agent stack; an agent is one way to implement them, and also something they serve. C changes the knowledge the agent can use.

The three paths move forward in parallel because their methods and failure modes are completely different; later we verify on the same batch of tasks whether they really complement each other, since gains do not simply add up.

The dual-loop architecture of the evolution loop

The three paths answer "what to change"; the dual loop answers another question: who proposes changes, who judges whether they help, and how those two jobs themselves get better. The first-order loop improves the strategy of the Executor (the agent being evolved) every round; the second-order loop reviews the first-order loop every n rounds and improves how it proposes and verifies changes.

"Strategy" here means the modifiable parts produced by the three paths: skills, tools, prompts, knowledge entries and so on.

What gets trained is the process judge model; the base model under the Executor stays unchanged.

13. Beyond functional correctness: non-functional requirements

Most existing RSI work focuses on the success rate / accuracy of task completion (functional correctness) and ignores software's non-functional requirements. Once our code is written, people remain responsible for it for a long time, so non-functional requirements matter a great deal. This is a key difference between our work and existing work.

Dimension Definition How it is extracted from trajectories How it is checked
Reliability Stability, fault tolerance, edge-case handling The user mentions "it keeps crashing", "edge cases aren't handled" Exception handling coverage, boundary checks
Usability Easy to use, follows conventions, interface design The user mentions "hard to use", "the interface isn't intuitive" Interface design guidelines, sensible parameters
Maintainability Easy to change, easy to extend, modular The user mentions "too painful to change", "the logic is too complex" Cyclomatic complexity, duplicate code, module coupling
Readability Easy to understand, commented, clear naming The user mentions "can't follow it", "missing comments" Naming conventions, comment completeness, code style
Performance Time efficiency, space efficiency The user mentions "too slow", "uses too much memory" Time complexity, memory usage, hotspot analysis
Security Input validation, permission checks, protection of sensitive data The user mentions "security issue", "permissions aren't checked" Static analysis (SQL injection, XSS), permission checks

The approach is to extract these concerns from what users say and how they edit code, run the matching checks (such as cyclomatic complexity, duplicate code, naming and comments, exception and edge-case handling), and extract tasks aimed specifically at non-functional requirements for evaluation and evolution.

14. The future: coding agents three years from now

If this works, the coding agent of 2028 gets better the more it is used on the user's own repository, no longer repeats mistakes it has been corrected on, and writes code that not only runs but is easy to maintain; adaptation to a new model is verified within a week of its release; obsolete skills in the skill library are retired automatically and effective ones promoted automatically.
