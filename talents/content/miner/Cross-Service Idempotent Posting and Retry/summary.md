# Cross-Service Idempotent Posting and Retry: Development Pattern Summary

> Scenario: idempotent cross-service reward posting. Implement idempotent cross-service reward posting, including a duplicate-evaluation check, account posting deduplication, keeping failures in pending status, and manual retry.
> Basis: `analyzer.md` (the marketing-service reward issuance + account-service idempotent posting case) and code snippets 01–03.

## 1. Overall pattern

| Dimension | Convention |
|---|---|
| Architecture | The initiator (such as the marketing/reward service) orchestrates "business record + downstream posting"; the receiver (such as the account service) offers idempotent writes keyed by a business idempotency key; the two services have separate databases and separate transactions |
| Consistency | Without MQ, use "local transaction + synchronous call + idempotency key + manual retry"; a downstream failure neither blocks nor is discarded, and the pending status is kept |
| Idempotency | **One guard at each end**: the initiator uses a unique constraint on the business natural key (prevents repeated evaluation/issuance); the receiver uses the business idempotency key (a globally unique ID generated by the caller) as the primary key to prevent duplicate posting; check-before-write in the application layer + database constraints as the concurrency safety net |
| Failure handling | Downstream exceptions become a domain exception (such as `RemoteServiceException`), and the transaction uses `noRollbackFor` on that exception to keep the state; the record moves to PENDING + failure reason; a manual retry entry is provided, and the retry is idempotent (short-circuits if already successful) |
| Layering | interfaces → application → domain ← infrastructure (no framework dependencies in the domain); repositories use port interfaces bridged to persistence implementations |
| Amounts/identifiers | `BigDecimal(N,2)` throughout, compared with `compareTo/signum`; idempotency keys are UUID strings (e.g. 36 characters); times are `LocalDateTime` + an injected `Clock` |
| Concurrency | Business entities carry an `@Version` optimistic lock; unique constraints/primary keys are the safety net for concurrent races |

## 2. Implementation steps

### Step 1: Create the record entity that carries idempotency (initiator)

**Implementation logic**: create a "grant/issuance record" entity that holds the business natural key, amount, state machine and failure reason; build a database unique constraint on the natural key as the final guarantee of the initiator's idempotency.

**Standards and constraints**:
- The table's unique key is the business natural key (e.g. `(campaign_id, transaction_id)`, named `uk_<table>_<key>`), with a query index to support exists/count.
- A state machine such as `PENDING → GRANTED / FAILED`, with transitions wrapped in methods (markGranted/markPending/markFailed) that maintain `failureReason`/`grantedAt` and other timestamps.
- The entity has an `@Version` optimistic lock column; amount columns are `precision=12, scale=2`; identifier column lengths match the legacy data dictionary.
- The constructor makes business assertions (e.g. the reward must be > 0) and throws the unified domain exception `BusinessRuleException("CODE", "message")`.
- Create the table with a Flyway migration; table names are lower case with underscores, and `@Column` maps one-to-one to SQL columns.

**Notes**: the unique constraint and the `exists` check in code are a double safeguard: the check prevents duplicates, the constraint prevents concurrent races. State methods are idempotent (repeating markGranted has no side effects).

**Historical reference code (generalized)**:
```java
@Entity
@Table(name = "<grant_record_table>", uniqueConstraints = @UniqueConstraint(name = "uk_<table>_<natural_key>",
        columnNames = {"<business_key_1>", "<business_key_2>"}))
public class <GrantRecord> {
    @Id @Column(name = "record_id", length = 36, updatable = false) private String recordId;
    @Version @Column(name = "version") private long version;
    public void markGranted(LocalDateTime now) { status = GRANTED; grantedAt = now; failureReason = null; }
    public void markPending(String reason)      { status = PENDING; failureReason = reason; }
    public void markFailed(String reason)       { status = FAILED; failureReason = reason; }
}
```

### Step 2: Define the repository port and implementation

**Implementation logic**: the domain layer defines the repository interface (idempotency check, counting, lookup by ID, save), and the infrastructure layer bridges it to derived queries with a Spring Data JPA interface + default methods, achieving dependency inversion.

**Standards and constraints**:
- Port method names carry meaning: `existsBy<NaturalKey>(...)`, `countBy<Dimension>(...)`, `findBy<Id>`, `save<Entity>`.
- The implementing interface extends both `JpaRepository` and the port interface, using default methods to map the meaningful names to derived queries; no Spring annotations appear on the entity.
- Paged/conditional queries use `JpaSpecificationExecutor` + dynamically combined `Predicate`s.

**Notes**: the domain interface imports no Spring classes; the `@Version` field is maintained by JPA automatically and needs no handling in the repository layer.

**Historical reference code (generalized)**:
```java
public interface <Entity>Repository {           // domain port
    Optional<X> findBy<Id>(String id);
    X save(X x);
    boolean existsBy<Key1>And<Key2>(String k1, String k2);
    long countBy<Dim>(String dim);
}
public interface <Entity>JpaRepository extends JpaRepository<X, String>, <Entity>Repository {  // infrastructure
    @Override default boolean existsBy<Key1>And<Key2>(String k1, String k2) {
        return existsBy<Field1>And<Field2>(k1, k2);
    }
    boolean existsBy<Field1>And<Field2>(String k1, String k2);  // Spring Data derived
}
```

### Step 3: Orchestrate the business logic (initiator application service)

**Implementation logic**: the application service injects the repository ports, the outbound client and `Clock`, and orchestrates in the order "validate → idempotency check → business decision → create record → call downstream → persist"; a downstream failure moves the record to pending status without interrupting other items in the same batch; a manual retry entry is provided.

**Standards and constraints**:
- Class-level transaction annotation `@Transactional(noRollbackFor = <RemoteException>.class)`: on a downstream failure the saved pending record is kept, not rolled back.
- Inside a loop/batch, an item that does not qualify only records the skip reason and continues; it does not throw and interrupt the whole batch.
- Idempotency: each item first checks `existsBy<NaturalKey>`; a hit records `ALREADY_*` and is skipped; repeated calls return the existing result.
- Retry entry: look up the record first; if already successful (`isGranted()`), short-circuit and return; if not successful and the downstream must be called, call it again (the downstream idempotency key is the safety net); on success move to GRANTED, on failure move to PENDING + save + throw (noRollbackFor keeps the state).
- Parameter validation sits at the application layer entry (non-null, digit format, amount > 0); failures throw `InvalidRequestException` (400); a missing record throws `NotFoundException` (404).
- Inject `Clock` as the time source and always use `LocalDateTime.now(clock)` so tests stay controllable.

**Notes**: putting the external call inside the transaction is an explicit trade-off of the "synchronous approach" (a long transaction holding locks), protected by noRollbackFor; every downstream failure point must try/catch and change state rather than throw upward; a single `Clock` for timestamps keeps tests controllable.

**Historical reference code (generalized)**:
```java
@Service
@Transactional(noRollbackFor = RemoteServiceException.class)
public class <OrchestrationService> {
    public <Result> evaluate(<Command> cmd) {
        validate(cmd);
        for (<BusinessItem> item : <repo>.findActiveAt(now)) {
            if (<repo>.existsBy<Key>(item.id, cmd.<businessId>())) { skipped(...ALREADY_*); continue; }
            // Business decision: not met → skipped(reason); met → build the record
            <Record> g = new <Record>(UUID.randomUUID().toString(), ..., now);   // initially PENDING
            try {
                <client>.<downstreamWrite>(cmd.accountId(), g.getId(), item.id, g.getAmount());
                g.markGranted(now);
            } catch (RemoteServiceException ex) {
                g.markPending("...: " + ex.getMessage());
            }
            <repo>.save(g);
        }
    }
    public <View> fulfill(String recordId) {   // manual retry
        <Record> g = <repo>.find(recordId).orElseThrow(NotFoundException);
        if (!g.isGranted()) { try { <client>.<downstreamWrite>(...); g.markGranted(now); }
            catch (RemoteServiceException ex) { g.markPending(ex.getMessage()); <repo>.save(g); throw ex; } }
        <repo>.save(g);
    }
}
```

### Step 4: Write the downstream outbound adapter (initiator)

**Implementation logic**: wrap the HTTP calls to the downstream service and isolate transport details: read endpoints distinguish "does not exist (404→empty)" from "real failure (non-2xx→domain exception)"; write endpoints POST with the idempotency key and business parameters; network exceptions are always wrapped as the domain `RemoteServiceException`.

**Standards and constraints**:
- Use `RestClient` (Spring Boot 3+), with baseUrl and timeouts wired by a configuration bean (e.g. a `@Qualifier`-named client).
- Read endpoints use `exchange()` to branch on status codes manually; write endpoints use `retrieve()`, and failures throw `RestClientException` → wrapped as `RemoteServiceException("<downstream name> unavailable/failed", ex)`.
- Request/response bodies are records; internal private records are converted to the domain model.
- The idempotency key travels with the request as one of the write endpoint's parameters (the downstream deduplicates by it).

**Notes**: do not swallow connection-level exception details; logs contain only business identifiers (such as transaction ID/record ID), never sensitive fields such as card numbers; timeouts must match the downstream SLA (3s in the example).

**Historical reference code (generalized)**:
```java
@Component
public class <Downstream>Client {
    private final RestClient restClient;
    public <Downstream>Client(@Qualifier("<downstream>RestClient") RestClient restClient) { this.restClient = restClient; }

    public Optional<Snapshot> find(String id) {
        try {
            return restClient.get().uri("/api/v1/<resource>/{id}", id)
                .exchange((request, response) -> {
                    if (response.getStatusCode().value() == 404) return Optional.empty();
                    if (!response.getStatusCode().is2xxSuccessful())
                        throw new RemoteServiceException("HTTP " + response.getStatusCode().value());
                    return Optional.of(parse(response.getBody()));
                });
        } catch (RestClientException ex) { throw new RemoteServiceException("<downstream> unavailable", ex); }
    }
    public void credit(String accountId, String idempotencyKey, BigDecimal amount) {
        try { restClient.post().uri("/api/v1/<resource>/{id}/<action>", accountId)
                .body(new CreditBody(idempotencyKey, amount)).retrieve().toBodilessEntity(); }
        catch (RestClientException ex) { throw new RemoteServiceException("<downstream> <action> failed", ex); }
    }
}
```

### Step 5: The downstream provides an idempotent write use case (receiver)

**Implementation logic**: the receiver adds an idempotent write use case: check-before-write by the business idempotency key passed in by the caller; if it already exists, return the current entity directly (no repeated change); otherwise perform the business change and record the "already processed" fact, both in the same local transaction.

**Standards and constraints**:
- The idempotency table uses the idempotency key as its primary key (e.g. `reward_credit(reward_id PK, ...)`); on a repeated call `existsBy<IdempotencyKey>` hits and returns directly.
- The business change is wrapped in an aggregate root method (e.g. `applyCashback(amount)`: validates > 0, with a comment explaining the balance direction).
- Write order: business entity first, then the idempotency record (same transaction); recording "already processed" first and then failing would leave a false record.
- Write the idempotency key semantics into comments and requirement documents (e.g. `NR-REWARD-01`), and validate API input with annotations (`@NotBlank`/`@DecimalMin`).

**Notes**: the idempotency key is generated by the caller and passed with the request (the receiver does not make its own key); avoid sign errors when the balance/amount direction is the opposite of posting; table and column names correspond to the legacy data dictionary.

**Historical reference code (generalized)**:
```java
@Service @Transactional
public class <Receiver>ApplicationService {
    public Account credit(String accountId, String idempotencyKey, BigDecimal amount) {
        if (<idempotencyTableRepo>.existsBy<IdempotencyKey>(idempotencyKey)) return getById(accountId);   // idempotent
        Account account = getById(accountId);
        account.apply<Action>(amount);
        Account saved = accounts.saveAccount(account);
        <idempotencyTableRepo>.save(new <IdempotencyRecord>(idempotencyKey, accountId, ..., amount, LocalDateTime.now()));
        return saved;
    }
}
```

### Step 6: Database migrations (both ends)

**Implementation logic**: the initiator's migration creates the business record table (unique constraint + index); the receiver's migration creates the idempotency table (idempotency key PK + query index). Evolve with Flyway versioning.

**Standards and constraints**:
- Table names are lower case with underscores, plural (e.g. `reward_grant`/`reward_credit`); migrations are named `V<N>__<topic>_schema.sql`.
- Unique constraint `CONSTRAINT uk_<table>_<key> UNIQUE (...)`; query index `CREATE INDEX idx_<table>_<column> ON <table> (<column>)`.
- Amounts `NUMERIC(12,2)` and identifiers `VARCHAR(length)` map one-to-one to the entity's `@Column`; the `@Version` column is `BIGINT NOT NULL DEFAULT 0`.

**Notes**: migrations run on both H2 (unit tests) and PostgreSQL, so keep the syntax compatible; constraint names are globally unique to avoid migration conflicts.

**Reference files**: `V1__marketing_schema.sql` lines 490–510; `V3__reward_credit.sql`, whole file.

### Step 7: Tests cover idempotency and failure paths

**Implementation logic**: the receiver uses `@SpringBootTest` + MockMvc end to end to verify that "repeated calls with the same idempotency key change state only once" (with the real constraints in effect); the initiator uses Mockito stubs for the repositories and client to verify issuance, PENDING, idempotent skips and retries.

**Standards and constraints**:
- Idempotency assertions: state/balance unchanged after repeated calls; `verify(repo, never()).save(...)` (a repeated evaluation does not save).
- Failure branch: `doThrow(RemoteServiceException)` → assert the record is PENDING with a reason; a successful retry moves it to GRANTED.
- Fixed `Clock` (e.g. `Clock.fixed(...)`); amount assertions use `isEqualByComparingTo`.
- Application tests use `@ExtendWith(MockitoExtension.class)` + `@Mock` ports; end-to-end tests use `@ActiveProfiles("test")`.

**Notes**: do not assert logs or implementation details; tests must not depend on external networks/other services; when verifying `never()`, also verify that the main-path call really happened (to avoid a false green from a missing stub).

## 3. Other concepts and best practices

- **Three options for cross-service consistency**: option A local transaction + synchronous call + idempotency key + manual retry (no middleware, short path, a downstream failure does not affect the main path); option B Outbox + MQ (full decoupling, replayable, higher cost); option C end-of-day batch (simple but not real time). Design the idempotency key to serve both synchronous retries and future event replay, to avoid rework.
- **Separate failure domains**: the failure domains of funds/accounting facts and add-on benefits (marketing rewards, notifications, etc.) must be separated: a failed add-on call only raises an alert and does not roll back; a downstream failure keeps a retryable pending status.
- **Three layers of idempotency**: check-before-write in the application layer → database unique constraint/primary key (concurrency safety net) → short-circuit at the retry entry (no repeated call once successful).
- **Optimistic locking**: business entities carry `@Version`, replacing the legacy "read-modify-write + manual comparison"; under extreme concurrency, resource counters (such as the budget) may be overspent and need reconciliation.
- **Unified exceptions and error body**: bad parameters `InvalidRequestException` (400), missing record `NotFoundException` (404), downstream unavailable `RemoteServiceException` (503); error response `{"code","message","details"}`; HTTP semantics 400/404/409/503.
- **Identifier and amount conventions**: legacy identifiers are zero-padded fixed-length strings (e.g. transaction ID 16 digits, card number 16 digits, account 11 digits); amounts are `BigDecimal`, `double` is forbidden; times are `LocalDateTime` with an injected `Clock`.
- **Observability and rollback**: logs contain only business identifiers, never sensitive fields; provide a configuration switch to turn off the downstream integration entirely (e.g. `marketing.enabled`); pending records get a query and management entry (operations can retry manually).
- **Test layers**: pure domain unit tests (no Spring) + application layer Mockito unit tests (stubbed ports/clients) + `@SpringBootTest`/MockMvc end to end (real constraints) + migrations run on both H2 and PostgreSQL.
