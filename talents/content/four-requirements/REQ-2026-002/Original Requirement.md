## 1. Background and Goals

### 1.1 Business Background

After a customer's card is lost or stolen, the card must be stopped immediately and a replacement requested; the current system only allows back-office maintenance of the card status, customers have no self-service entry point, replacement progress is not visible, and customer service tickets are concentrated on progress queries.
This phase provides customer self-service loss reporting, replacement requests, and replacement progress viewing, and gives operations a replacement queue workbench.

### 1.2 Business Goals (Quantifiable)

| Goal | Quantified metric |
|------|---------|
| Shorten card blocking time | Average time from loss report acceptance to the card status taking effect drops from 15 minutes to 1 minute |
| Reduce customer service workload | Replacement progress inquiries drop 40% (against the 3-month average before launch) |
| Improve turnaround | Loss reporting API p95 < 500ms; replacement request p95 < 1200ms |

### 1.3 Glossary

| Term | Definition |
|------|------|
| Card loss reporting | The customer proactively declares that the card is lost or stolen; the system immediately sets the card status to `LOST` and blocks transactions |
| Replacement ticket | The business document recording the entire replacement request flow, with statuses REQUESTED→CARD_PRODUCED→SHIPPED→ACTIVATED/CANCELLED |
| Card production | The step in which the card network or a card manufacturer produces the physical card with the new card number |
| Tracking number | The waybill number filled in during mailing for the customer to view on the progress page |
| Activation | The first activation of a new card; the card cannot be used for transactions before activation |
| Deduplication key | A business-unique key generated by the client (API field `idempotencyKey`); resubmitting the same key returns the same result |

| Role | Responsibilities | Permission points |

## 3. Scope Definition

### 3.1 In-Scope / Out-of-Scope

**In-Scope**

- Card loss reporting (immediate hold), replacement requests, replacement progress, replacement tickets.
- Replacement fee (simulated 50.00) charged to the account.
- New card number generation and old card invalidation, notifications, audit.
- Front-end card details, loss reporting wizard, progress page; back-office replacement queue.

**Out-of-Scope**

- Real-time courier tracking (only the tracking number and mailing status are recorded).
- Overseas emergency replacement, temporary virtual cards.
- Handling disputed transactions after a loss report (see REQ-2026-004).

### 3.2 Assumptions and Dependencies

| ID | Assumption/Dependency | Description |
|------|----------|------|
| A-01 | card-service provides the card state machine and supports the `LOST` status | This requirement extends state transitions and does not create a card table |
| A-02 | Fees are posted through the `FEE` batch of transaction-service | The replacement fee does not use a separate charging channel |
| A-03 | Account balance changes are completed by account-service | The replacement fee affects the available balance and the general ledger |
| A-04 | Tracking numbers are filled in manually by card production operations | No courier API integration in this phase |
| A-05 | Notifications use notification-service templates | Notification failures do not roll back loss reporting or replacement |

### 4.2 Detailed Functional Requirements

#### REQ-2026-002-01 "Report loss" entry on card details (REQ-LOST-01)

**Description**: On the card details page, show a "Report loss" button for `ACTIVE` cards, which opens a loss reporting confirmation dialog (risk warning, reason selection, entry of the last 4 digits of the card number); the entry is not shown for cards that are not `ACTIVE`.

**Field-level requirement table**:

| Field | Type | Required | Format/Validation | Default | Source |
|------|------|------|----------|--------|------|
| cardNumber | string(19) | Yes | 16-digit numeric string; must belong to the current logged-in customer | None | Route path parameter |
| cardStatus | string(16) | Yes | The entry is shown only for `ACTIVE` | `ACTIVE` | card-service |
| reason | string(16) | Yes | Enum `LOST`/`STOLEN`/`DAMAGED` | None | Front-end dropdown |
| confirmCardLast4 | string(4) | Yes | 4 digits, must match the last 4 digits of the card number | Empty | Front-end input |

**Exception matrix**:

| Exception scenario | System behavior | Error code | User message |
|---------|---------|--------|---------|
| Card is not `ACTIVE` (lost/held/closed) | Do not show the loss reporting button | `CARD_NOT_ACTIVE` | "The current card status does not support loss reporting" |
| The last 4 digits of the card number are wrong | The front end blocks it and no request is sent | None (front-end validation) | "The last 4 digits of the card number do not match" |
| The card does not belong to the current customer | Return 404 without revealing that the card exists | None (`404`) | "Card not found" |
| card-service timeout (> 500ms) | Disable the button and show a retry action | `DOWNSTREAM_UNAVAILABLE` | "Failed to load card information; please retry" |

#### REQ-2026-002-02 Loss reporting takes effect immediately (REQ-LOST-02)

**Description**: After the customer confirms, the card status changes immediately from `ACTIVE` to `LOST`, blocking subsequent transaction authorizations; a `card_operation` record and an audit event are written, and a notification is sent.

**Field-level requirement table**:

| Field | Type | Required | Format/Validation | Default | Source |
|------|------|------|----------|--------|------|
| idempotencyKey | string(64) | Yes | Generated by the client, unique; resubmission returns the first result | None | Front end |
| cardStatus | string(16) | Yes | Transitions from `ACTIVE` to `LOST` and cannot be reverted | None | card-service state machine |
| operationType | string(16) | Yes | Fixed `LOSS` | `LOSS` | card-service |
| actor | string(64) | Yes | Customer number or customer service employee number, taken from the token | None | IAM token |
| maskedCardNumber | string(19) | Yes | Only the first 6 and last 4 digits are stored, with \* masking in between | Computed value | card-service |

**Exception matrix**:

| Exception scenario | System behavior | Error code | User message |
|---------|---------|--------|---------|
| Card already lost, duplicate submission | Return the first result (HTTP 200) without a duplicate notification | `CARD_ALREADY_LOST` | "This card has already been reported lost; no further action is needed" |
| The same deduplication key submitted 3 times | Only 1 `card_operation` record is created | None (deduplication hit) | "Loss reporting has taken effect" |
| Concurrent state transition conflict (version mismatch) | Optimistic locking rejects and asks for a refresh | `CONCURRENT_MODIFICATION` | "The card status has changed; refresh and retry" |
| notification-service failure | Loss reporting still takes effect, and the failed notification is recorded for redelivery | None (main flow succeeded) | "Loss reporting has taken effect; the notification will arrive shortly" |
| Audit write failure | Loss reporting takes effect and a local compensation log is written | None (main flow succeeded) | "Loss reporting has taken effect" |

#### REQ-2026-002-03 Replacement request (REQ-LOST-03)

**Description**: After reporting a loss, the customer requests a replacement, confirms or changes the delivery address, selects the replacement reason and delivery method, and after confirming the fee creates a replacement ticket and generates a new card number; the old card is permanently invalidated.

**Field-level requirement table**:

| Field | Type | Required | Format/Validation | Default | Source |
|------|------|------|----------|--------|------|
| cardNumber | string(19) | Yes | Must be in `LOST` status and belong to the current customer | None | Route path parameter |
| addressId | string(32) | Yes | Exists in the customer's address book | Default address | customer-service |
| deliveryMethod | string(16) | Yes | Enum `STANDARD`/`EXPRESS` | `STANDARD` | Front-end selection |
| reason | string(16) | Yes | Enum `LOST`/`STOLEN`/`DAMAGED` | Inherited from the loss report | Front-end dropdown |
| feeAmount | decimal(12,2) | Yes | ≥ 0; 0.00 for platinum cards, 50.00 for the rest | Value by card tier | Pricing rules |
| newCardNumber | string(19) | Yes | 16 digits, BIN range consistent with card network specifications, unique | Generated by the server | card-service |
| idempotencyKey | string(64) | Yes | Unique; the same key returns the same ticket | None | Front end |

**Exception matrix**:

| Exception scenario | System behavior | Error code | User message |
|---------|---------|--------|---------|
| The card already has a replacement ticket in progress | Reject creation and return the existing ticket | `REPLACEMENT_EXISTS` | "A replacement request is already in progress for this card" |
| The card is not in `LOST` status | Reject creation | `CARD_NOT_ACTIVE` | "Please report the loss before requesting a replacement" |
| The address ID does not exist or does not belong to the customer | Parameter validation fails | `INVALID_ADDRESS` | "The delivery address is invalid; please select another one" |
| New card number generation fails (number range exhausted or check digit conflict) | The ticket stays `REQUESTED` and an alert is raised, with retry supported | `CARD_NUMBER_GENERATION_FAILED` | "The replacement request has been accepted; card production details are being generated" |
| Duplicate submission with the same deduplication key | Return the ticket created the first time | None (deduplication hit) | "The replacement request has been submitted" |

#### REQ-2026-002-04 Replacement progress (REQ-LOST-04)

**Description**: Customers view the replacement ticket timeline (requested → in production → shipped → activated); after operations update the status, it is immediately visible on the customer side; customers are read-only and cannot change the status.

**Field-level requirement table**:

| Field | Type | Required | Format/Validation | Default | Source |
|------|------|------|----------|--------|------|
| replacementId | string(32) | Yes | Exists and the ticket belongs to the current customer | None | Route path parameter |
| status | string(16) | Yes | Enum `REQUESTED`/`CARD_PRODUCED`/`SHIPPED`/`ACTIVATED`/`CANCELLED` | `REQUESTED` | card_replacement |
| trackingNo | string(32) | No | Required only after `SHIPPED` | Empty | Filled in by operations |
| estimatedArrival | date | No | Shown only after `SHIPPED`, ≥ shipping date + 3 days | Empty | Filled in by operations |
| statusUpdatedAt | timestamptz | Yes | Refreshed on every state transition | Creation time | card-service |

**Exception matrix**:

| Exception scenario | System behavior | Error code | User message |
|---------|---------|--------|---------|
| The ticket does not belong to the current customer | Return 404 | None (`404`) | "No replacement record found" |
| Status is `SHIPPED` but the tracking number is empty | Show "Logistics information is syncing" and let customer service step in | `TRACKING_MISSING` | "Logistics information is syncing; please contact customer service" |
| Operations fills in an invalid state transition (such as `REQUESTED` directly to `ACTIVATED`) | Reject the update | `INVALID_STATE_TRANSITION` | Back office shows "Invalid state transition" |

#### REQ-2026-002-05 Replacement fee collection (REQ-LOST-05)

**Description**: The application page shows the replacement fee; after confirmation the fee is charged to the account and the general ledger through the `FEE` batch of transaction-service; if posting fails, the ticket is kept and marked `FEE_PENDING`, with retry collection supported.

**Field-level requirement table**:

| Field | Type | Required | Format/Validation | Default | Source |
|------|------|------|----------|--------|------|
| feeAmount | decimal(12,2) | Yes | ≥ 0, 0.00 for platinum cards, 50.00 for the rest | Value by card tier | Pricing rules |
| feeBatchId | string(32) | No | Filled in after successful posting, unique | Empty | transaction-service |
| feeStatus | string(16) | Yes | Enum `CHARGED`/`FEE_PENDING`/`WAIVED` | `CHARGED` | card-service |
| accountId | string(20) | Yes | The account linked to the ticket; must exist | Account linked to the card | account-service |

**Exception matrix**:

| Exception scenario | System behavior | Error code | User message |
|---------|---------|--------|---------|
| transaction-service posting fails | The ticket is kept, marked `FEE_PENDING`, and enters the retry queue | `FEE_POSTING_FAILED` | "The replacement request has been accepted; the fee will be collected within 24 hours" |
| The same ticket triggers the charge repeatedly | Deduplicated by `feeBatchId`, so no double charge | None (deduplication hit) | No message |
| Platinum card fee is 0.00 | No posting is created and `feeStatus` is set to `WAIVED` | None | "Platinum cards are exempt from the replacement fee" |
| Insufficient account balance | Allow the amount owed to be posted and accrue interest per the existing statement rules | None | "The fee has been posted" |

## 5. Business Rules

| ID | Rule | Source | Priority | Verification point |
|------|------|------|--------|--------|
| BR-LOST-01 | Only `ACTIVE` cards can be reported lost; already lost/held/closed cards return 409 | Simulated business confirmation | Must | Calling the loss reporting API for all three non-ACTIVE card types returns `CARD_NOT_ACTIVE` |
| BR-LOST-02 | Loss reporting cannot be undone; replacement can be cancelled (before card production) | Simulated business confirmation | Must | The loss reporting API has no undo path; cancelling after `SHIPPED` returns `REPLACEMENT_NOT_CANCELLABLE` |
| BR-LOST-03 | Replacement fee 50.00, free for platinum cards; the fee is charged to the account | Simulated pricing | Must | Platinum card `feeStatus=WAIVED`; gold/classic cards post a 50.00 FEE |
| BR-LOST-04 | Replacement generates a new card number and the old card is permanently invalidated; the new card cannot be used for transactions before activation | Simulated business confirmation | Must | Authorization on the old card number is declined; transactions on the new card are declined before `ACTIVATED` |
| BR-LOST-05 | Replacement ticket statuses: REQUESTED→CARD_PRODUCED→SHIPPED→ACTIVATED/CANCELLED | Simulated business confirmation | Must | Invalid transitions are rejected with `INVALID_STATE_TRANSITION` |
| BR-LOST-06 | Only one replacement ticket in progress per card at a time | Simulated business confirmation | Must | With two concurrent requests, `card_replacement` has only 1 record in progress |
| BR-LOST-07 | Loss reporting/replacement must write an audit record (actor, masked card number, reason) | Simulated compliance | Must | The audit event contains the actor, maskedCardNumber, and reason fields |

## 6. Non-Functional Requirements

### 6.1 Performance, Availability, and Observability

| Dimension | Metric | Verification method |
|------|------|---------|
| Performance | Loss reporting p95 < 500ms; replacement request p95 < 1200ms; progress query p95 < 800ms | Load test with 50 concurrent users and take p95 |
| Availability | Unavailable dependencies return a clear error code; loss reporting is not affected by notification failures | Report a loss after stopping notification-service and assert that the card status is LOST |
| Consistency | Loss reporting and the card status transition complete in the same transaction | With concurrent loss reports, assert that only 1 `card_operation` record exists |
| Deduplication | Loss reporting and replacement requests support deduplication; duplicate requests return the first result | Submit the same deduplication key 3 times and assert that the record count is 1 |
| Observability | Every state transition outputs traceId, cardNumberLast4, and replacementId | Verify through log search and metrics |
| Maintainability | The state machine and fee rules are configurable, so new delivery methods require no code changes | Code review + configurable test cases |

### 6.2 Security Requirements

| Dimension | Requirement | Verification method |
|------|------|---------|
| Authentication | All APIs require a JWT issued by IAM; requests without a token return 401 | Call the 7 APIs without a token |
| Authorization | Customers can operate only on their own cards; unauthorized access returns 404; back-office APIs are for role `A` only | Use customer A's token to operate on customer B's card |
| Identity verification | Loss reporting requires the last 4 digits of the card number; customer service reporting on behalf of a customer requires the ticket number + an identity verification record | The customer service UI forces entry of the verification method |
| Data protection | Card numbers are shown with only the last 4 digits in logs, events, and responses; the database stores masked and encrypted card numbers in separate columns | Search logs for full card numbers (should be 0 hits) |
| Abuse prevention | More than 3 loss reporting requests from the same customer within 24 hours triggers a risk alert | Send 4 requests and assert the alert event |
| Audit | Loss reporting, replacement, status updates, and fee posting write audit records | Query audit-service events for completeness |

### 8.2 Data Security

| Dimension | Requirement |
|------|------|
| Masking | Card numbers show only the last 4 digits in API responses, logs, and audit events; the page displays them as `\*\*\*\* \*\*\*\* \*\*\*\* 5740` |
| Encryption | Full card numbers are stored in a ciphertext column (AES-256, keys managed by KMS); HTTPS at the transport layer |
| Retention | Loss reporting and replacement tickets are retained for 5 years; audit events for 3 years; tracking numbers for the same period as the ticket |
| Access | Customers can access only their own cards and tickets; operations can view all tickets but cannot change card numbers; exported files expire automatically after 24 hours |
| Minimization | Customer ID document images and detailed home addresses are not collected; only `addressId` is referenced |

## 9. Scenario Matrix

| Type | Scenario | Role | Data/API | Expectation |
|------|------|------|-----------|------|
| Main flow | Report an `ACTIVE` card lost | Cardholder | POST `/cards/4000000000005740/loss` | 201, `cardStatus=LOST`, 1 new `card_operation` record, notification sent |

## 10. Acceptance Criteria (Executable)

| Story | Given | When | Then | Data preparation |
|------|-------|------|------|---------|
| US-001 | An `ACTIVE` card 4000000000005740 exists | The customer confirms the loss report | The card status becomes `LOST` immediately, authorization on the old card is declined, and the audit is queryable | Card and account 00000000006 |
| US-002 | The card is already `LOST` | Submit the loss report again | 409 `CARD_ALREADY_LOST`, and only 1 notification exists | Reuse US-001 data |
| US-003 | A platinum card has been reported lost | Submit a replacement request | `feeAmount=0.00`, `feeStatus=WAIVED`, no FEE posting | Platinum card 4000000000009999 |
| US-004 | A gold card has been reported lost | Submit a replacement request | `feeAmount=50.00`, a FEE posting is created, and `fee_batch_id` is filled in | Gold card 4000000000005740 |
| US-005 | A replacement ticket is in progress | Submit a replacement request again | 409 `REPLACEMENT_EXISTS`, and the ticket count does not change | Reuse US-004 data |
| US-006 | The ticket status is `CARD_PRODUCED` | Operations updates it to `SHIPPED` and fills in the tracking number | The customer progress page shows the tracking number and estimated arrival date | Ticket `replacement_id` |
| US-007 | A new card has been generated but not activated | Initiate a transaction with the new card | The transaction is declined with the message "The new card is not activated" | New card number + transaction request |
| US-008 | transaction-service is stopped | Submit a gold card replacement request | The ticket is created successfully with `feeStatus=FEE_PENDING`; the fee is collected within 24 hours after recovery | Stop and restore the container |

## 11. Dependencies and Constraints

### 11.1 Dependencies

| Dependency | Purpose | Impact of failure and handling |
|---------|------|---------------|
| card-service | Card state machine, card number generation | Loss reporting and replacement unavailable, returns 503 |
| customer-service | Address book lookup and validation | Replacement request rejected with an invalid address message |
| transaction-service | Replacement fee FEE posting | The ticket keeps `FEE_PENDING` and the charge is retried |
| account-service | Balance and statement update | The fee is posted later and the ticket is not blocked |
| notification-service | Loss reporting and replacement notifications | The main flow is not rolled back and redelivery is recorded |
| audit-service | Audit events | Write failures go to a local compensation log |
| IAM | Authentication and roles | Without a token, 401 is returned |

### 11.3 Constraints

- Reuse card-service; do not create a separate replacement service.
- Card number generation must comply with the card network BIN ranges and the Luhn check rule.
- Amounts uniformly use `BigDecimal` / `numeric(12,2)`.
- All write APIs support a deduplication key; key operations write audit events.
- The demo environment keeps the IAM roles `U`/`A`; the POC does not enforce API-level authorization (ADR-007), but card ownership validation must be retained.

## 12. Risks and Assumptions

### 12.1 Risks and Mitigations

| Risk/Assumption | Impact | Mitigation |
|-----------|------|------|
| The new card number generation rule (BIN range and check digit) is not aligned with card network specifications | The card number is invalid and the physical card cannot be used | Before launch, validate 1000 card numbers with the card network test range, all passing the Luhn check |
| The replacement fee waiver policy is a simulated value | Customer complaints or revenue deviation | Only configuration changes after pricing confirmation; configuration items are marked `SIMULATION` before v1.1 |
| Tracking numbers rely on manual entry | The customer progress page shows no logistics information for a long time | If nothing is filled in within 24 hours after `SHIPPED`, an operations alert is triggered |
| The customer requests a replacement immediately after the loss report and the address has become invalid | Replacement mailing fails | Validate the address through customer-service at request time |
| Assumption: no cap on replacement tickets per card | Malicious repeated requests | More than 3 requests within 24 hours triggers a risk alert and manual review |

### 12.2 Assumptions

- The old card is invalidated immediately after the loss report, with no grace period.
- The card production and mailing cycle is determined by the card network and the courier, and the system only records the status.

### 12.3 Items to Be Confirmed

1. Whether a replacement is initiated automatically after a loss report (to be confirmed: manual initiation by default; to become an optional automatic mode after product confirmation).
2. Whether customers can cancel a replacement and up to which status cancellation is allowed (to be confirmed: currently designed as cancellable before card production).
3. The new card number generation rule and BIN range for replacements (to be confirmed: alignment with card network specifications).
4. The replacement fee waiver policy and the platinum card scope (to be confirmed: pricing and product confirmation).
5. Whether the replacement fee debt counts toward the minimum payment amount (to be confirmed: confirmation by the statement rules owner).
