# pm-gate-checklist 技能

## 概述

本技能用于确保银行交付流水线各阶段产出与审批状态完整，支持阶段门禁决策。银行生产交付采用 G1–G8 八阶段门禁模型（需求签字 → 设计批准 → 代码评审 → 测试退出 → 安全放行 → 变更批准 → 发布执行 → 实施后复核），任一门禁缺失都可能导致阶段评审无法放行、上线窗口被冻结或事后审计追溯困难。

**核心价值：**
- 把"门禁状态靠人记"升级为"状态自动采集 + 证据链接矩阵"，消除状态滞后与口径不一
- 强制缺失项标注原因 + 责任人 + 预计闭环时间，避免"挂账式缺失"长期占位
- 提供与 CAB/ARB/合规评审对齐的标准化评审材料模板
- 在 L3 实施级下覆盖资金安全/监管报送/跨系统集成等高风险门禁的深度证据要求

## 工作流

### Step 1: 确定阶段与门禁范围

读取本阶段评审通知或里程碑计划，明确：

- [ ] 当前阶段属于 G1–G8 中的哪一档？（参考 `references/gate-definitions.md`）
- [ ] 本次评审是否涉及高风险场景？（资金安全/监管报送/跨系统集成/首次上线/限额参数变更）
- [ ] 若涉及高风险场景，自动升 L3，需通过下方「深度档位（L3 实施级）」全部可计算门禁
- [ ] 列出本阶段对应的门禁产出物清单（如 G4 阶段需有测试退出报告、缺陷收敛证据、性能基线对比）

### Step 2: 拉取本阶段各 Agent 产出

按门禁清单收集各 Agent 的产出物：

| 产出来源 | 产出物 | 收集方式 |
|---------|-------|---------|
| BA | 需求说明书、澄清清单、业务规则溯源 | 文档库链接 |
| Arch | 设计文档、ADR、影响分析 | 文档库 + ALM |
| Dev | MR、单元测试报告、静态扫描结果 | CI/ALM API |
| QA | 测试退出报告、缺陷清单、性能基线 | ITSM/ALM |
| Sec | 安全放行意见、漏洞处置清单 | 安全平台 |
| Release | RFC、回滚方案、发布计划 | ITSM |
| Ops | 发布记录、PIR、监控告警快照 | ITSM/监控平台 |

> 原则：能自动采集的不靠人工录入；不能自动采集的，由 PM 向责任人收集证据链接并归档。

### Step 3: 自动采集门禁状态

运行 `scripts/gate_collect.py <status_json> [--json]`，从本地状态 JSON（生产环境对应 ALM/CI/ITSM 三源对齐后的快照）汇总门禁状态：

- 输入：`{G1:{status, approver, evidence_url, ...}, G2:{...}, ...}`
- 输出：`{gates, missing, all_passed}` JSON
- 退出码：0=全部通过，2=存在未通过门禁，3=参数错误

> 状态 JSON 的关键字段：`status`（通过/PASS 视为通过，其他均为缺失）、`approver`、`evidence_url`、`collected_from`（ALM/CI/ITSM）、`collected_at`。

### Step 4: 对照门禁清单逐项核对

按 `templates/gate-checklist-template.md` 逐项填写：

1. **状态标注**：通过 / 缺失 / 待办 / 不适用（N/A 须注明原因）
2. **证据链接**：填写可访问的 URL 或文档库路径（无 404、无占位符）
3. **审批人留痕**：姓名 + 角色 + 审批时间 + 审批意见
4. **缺失项处理**：
   - 缺失原因分类（待产出 / 待评审 / 待审批 / 待集成 / 待外部依赖）
   - 责任人（必须为单人，避免责任稀释）
   - 预计闭环时间（必须早于下一阶段评审时间）
   - 替代证据或临时缓解措施（高风险门禁必填）

### Step 5: 生成评审材料

汇总形成评审材料包：

- **门禁检查清单**（主表）：G1–G8 状态总览，缺失项红色标注
- **证据链接矩阵**（L3 必填）：每门禁 → 证据 URL → 采集来源 → 采集时间
- **缺失项汇总**：按"缺失原因"分类统计，列出闭环计划
- **风险与替代证据**（L3 必填）：高风险门禁缺失时的替代证据或缓解措施
- **审批留痕表**（L3 必填）：所有审批人的姓名/角色/时间/意见
- **结论页**：放行 / 有条件放行 / 不放行，PM 与阶段负责人签字

### Step 6: 评审与定稿

- L2 评审：PM + 阶段负责人确认，签字归档
- L3 评审：ARB/合规评审 + 深度门禁全通过，缺一不可
- 评审退回：缺失项未闭环或证据不足，退回修订后重新评审

## 档位切换规则

| 档位 | 触发条件 | 审批要求 |
|------|---------|---------|
| L1 草稿 | 内部进度对齐、非正式同步 | 无需评审 |
| L2 标准（默认） | 银行生产默认档，常规阶段门禁评审 | PM + 阶段负责人确认 |
| L3 实施级 | 涉及资金安全/监管报送/跨系统集成/首次上线/高风险变更的门禁 | ARB/合规评审 + 深度门禁全通过 |

**自动升 L3 场景**：涉及反洗钱、限额参数、客户资金、监管报送、跨行接口、生产数据变更的门禁评审时，自动从 L2 升 L3；L3 须通过下方「深度档位（L3 实施级）」章节的全部可计算门禁。

## 深度档位（L3 实施级）

| 档位 | 要求 |
|------|------|
| L1 | 骨架要点，用于讨论 |
| L2 | 标准评审级（银行生产默认） |
| L3 | 在L2基础上增加以下深度内容（高风险/监管/复杂集成时必用） |

### L3 工作流补充

- **门禁证据链接矩阵**：G1–G8 每门禁 → 证据 URL → 采集来源（ALM/CI/ITSM）→ 采集时间 → 校验状态（可访问/404/占位符）
- **多源状态采集**：ALM（需求/缺陷/测试用例状态）、CI（构建/扫描/MR 状态）、ITSM（变更/发布/工单状态）三源对齐，状态不一致时以最严格口径为准并标注差异
- **缺失原因分类详表**：待产出 / 待评审 / 待审批 / 待集成 / 待外部依赖，每类有对应的闭环 SLA
- **审批人留痕**：每门禁审批人姓名 + 角色 + 审批时间 + 审批意见，禁止"全量同意"无意见通过
- **替代证据**：高风险门禁缺失时，须提供替代证据（如临时缓解措施、补偿控制）并经合规确认

### L3 质量门禁

- [ ] G1–G8 逐项有状态（通过/缺失/待办/N/A，N/A 须注明原因）
- [ ] 缺失项 100% 有原因 + 责任人 + 预计闭环时间（早于下阶段评审）
- [ ] 证据链接矩阵覆盖全部通过门禁，无 404、无占位符
- [ ] 状态源映射完整（ALM/CI/ITSM 至少一源，三源对齐时记录差异）
- [ ] 审批人留痕完整（姓名/角色/时间/意见四要素齐全）
- [ ] 高风险门禁缺失时有替代证据或缓解措施，经合规确认
- [ ] gate_collect.py 退出码 0（全部通过）或缺失项已全部纳入闭环计划

> 主模板含【L3必填】深度字段：`templates/gate-checklist-template.md`；详细档位定义见《Skill深度分级规范》。

## 模板

| 模板 | 用途 |
|------|------|
| `templates/gate-checklist-template.md` | 门禁检查清单（含 L2 基础字段与【L3必填】深度字段） |

### 模板使用要点

- L2 评审：填写 G1–G8 主表的状态/产出/审批人/缺失原因/责任人即可
- L3 评审：在主表基础上扩展证据链接矩阵、缺失原因详表、自动采集状态源映射、审批人留痕表
- 状态值统一使用：通过 / 缺失 / 待办 / 不适用（N/A），避免"OK""done""完成"等口语化表述

## 脚本

| 脚本 | 用途 | 退出码 |
|------|------|--------|
| `scripts/gate_collect.py` | 从状态 JSON 汇总门禁状态，输出通过/缺失清单 | 0/2/3 |

### 脚本使用示例

```bash
# 基本校验（使用本地状态 JSON）
python skills/pm-gate-checklist/scripts/gate_collect.py gate-status.json

# JSON 输出（供 Agent 消费）
python skills/pm-gate-checklist/scripts/gate_collect.py gate-status.json --json > gate-report.json
```

### JSON 输出示例

全部通过：
```json
{
  "gates": {
    "G1": {"status": "通过", "approver": "业务负责人"},
    "G2": {"status": "通过", "approver": "ARB"}
  },
  "missing": [],
  "all_passed": true
}
```

存在未通过门禁：
```json
{
  "gates": {
    "G1": {"status": "通过"},
    "G2": {"status": "待评审", "approver": "ARB"},
    "G3": {"status": "PASS"},
    "G4": {"status": "缺失"}
  },
  "missing": ["G2", "G4"],
  "all_passed": false
}
```

> 退出码：0=全部通过，2=存在未通过门禁（missing 非空），3=参数错误（文件不存在/JSON 解析失败）。

## 常见失败模式与规避

| 失败模式 | 表现 | 规避措施 | 重试策略 |
|---------|------|---------|---------|
| 状态滞后 | 门禁清单状态停留在上周，与 ALM/ITSM 实际状态不一致 | gate_collect.py 自动采集 + 采集时间戳；状态超过 24h 自动标"待刷新" | 重新拉取状态 JSON 后重跑 gate_collect.py |
| 缺失项无解释 | 缺失项只标"未完成"，无原因/责任人/闭环时间 | 模板强制缺失原因+责任人+预计闭环时间三字段；缺一不可 | 退回补全后重新提交评审 |
| 证据链接失效 | 证据 URL 404 或指向占位符 `{{待补}}` | 评审前脚本校验链接可访问性；占位符命中即标红 | 修复链接后重新校验 |
| 审批人留痕不全 | 只有姓名，无角色/时间/意见 | L3 强制四要素齐全；"全量同意"无意见退回 | 补充留痕后重新提交 |
| 多源状态不一致 | ALM 显示通过、CI 显示失败，未做对齐 | 三源对齐策略：以最严格口径为准，记录差异原因 | 人工确认后更新状态 JSON |
| 高风险门禁缺替代证据 | G5 安全放行缺失但无替代缓解措施 | L3 强制高风险门禁缺失须提供替代证据 + 合规确认 | 补充替代证据或等待原证据闭环 |

## 升级路径

| 升级方向 | 触发条件 | 增量字段 | 回退条件 |
|---------|---------|---------|---------|
| L1 → L2 | 进入正式阶段门禁评审 | 全部【L2必填】章节（门禁清单/评审材料/缺失原因/责任人） | 评审退回，降为草稿 |
| L2 → L3 | 资金安全/监管报送/跨系统集成/首次上线/高风险变更 | 证据链接矩阵、缺失原因详表、自动采集状态源映射、审批人留痕 | 风险降级或场景简化，经合规确认可回 L2 |

**人工兜底点**：L3 的门禁缺失原因与替代证据须由 PM 与阶段负责人共同确认；Agent 起草，PM 确认后定稿。降级须经 PMO + 合规审批并记录原因。审批人留痕的修改须经原审批人复核，不得由 PM 单方面代签。
